## What it is

A workbench for building software with Claude across every repo and machine you have: a live board of every git repo under a folder, shells that outlive the page, and Claude Code, Codex or Google Antigravity run as shells, jobs, chats and workflows. Web UI and a full CLI.

## Who uses it

One developer (the owner) across a laptop, an always-on Linux backend, a tablet and a phone, all on one tailnet, and the people the owner lets in: each backend keeps its own roster of people with a role (owner, admin, member, viewer) and teams (FR-074). Agents use it too: Claude sessions run inside its shells and drive it through the CLI, the HTTP API and `canopy mcp`, an MCP server over that API with the token the session holds. A backend is one trust domain: everyone signed in to it acts as the one OS user canopy runs as, so groups that must not reach each other's files each get a backend: a tenant (`canopy tenant add`), which on the mini is a compose project that mounts only its own folder. A public name is served only behind an authenticating proxy (Cloudflare Access). The proxy is still needed with caller tokens on: they guard what a call may change, but reads stay open and canopy has no sign-in for reading, so without the proxy anyone who reaches the name can read everything canopy shows.

## Stack and versions

- Bun 1.4.2 runs the server, the CLI and the tests (`bun test`).
- Docker uses Bun 1.4.4, pinned by digest in `Dockerfile` to the base the running shells were built on; changing it requires a planned shells restart.
- TypeScript 7.0.2, `strict` in both `tsconfig.json` and `ui/tsconfig.json`.
- React 19.3.1, Zustand 5.0.16, Vite 8.3.5 with @vitejs/plugin-react 6.1.2 for the SPA; a second Vite build makes the service worker (`ui/sw.ts`) into `dist/web/sw.js`.
- @xterm/xterm 6.0.0 for shells; tmux on the backend keeps them alive.
- ai 7.0.153 and @ai-sdk/gateway 4.0.126 for commit message suggestions.
- oxlint 1.89.0 for lint, configured in `.oxlintrc.json`; a hook called after an early return fails lint (`react/rules-of-hooks`).
- Plain CSS in `ui/src/styles.css`; no CSS framework.
- Instrument Sans and JetBrains Mono as bundled variable fonts (@fontsource-variable 5.3.0), so a page never fetches a font.
- git, gh and the `claude` CLI are shelled out to, never linked.
- Floorplan (MIT, haydenschmitty/floorplan) is vendored in `lib/floorplan` at the release its `VENDOR.md` pins, for the repo map (FR-070). `bun run floorplan:update` pulls a newer release and merges canopy's edits into it, and the repo's health check `floorplan` goes down when one is out. Its scripts and the map's server run on the machine's node, or on bun through a link named `node` where there is none.
- Archify (Apache-2.0 since 3.3.0, tt-a1i/archify) is vendored in `lib/archify` at the release its `VENDOR.md` pins, for the map section's diagrams (FR-071) and its Architecture Diagnosis (FR-075), which is the copy's Code Analysis module run by the backend itself. Its skill folder is upstream's byte for byte; canopy adds only the plugin manifest. Its CLI runs on the same node as Floorplan's, and its own update check is off: `bun run archify:update` moves it to a newer release, and canopy's health check `archify` says when one is out.
- Understand-Anything (MIT, Egonex-AI/Understand-Anything) is vendored in `lib/understand-anything` at the release its `VENDOR.md` pins, for the map section's knowledge graph (FR-072): upstream's plugin folder without its hooks, MCP package and pnpm files, with canopy's own `bun.lock`. Each backend installs and builds it with bun into its config dir on first use, so neither the repo nor the image holds its build. `bun run understand:update` pulls a newer release, and the repo's health check `understand` goes down when one is out.
- age-encryption 0.3.1 seals the secret store's values; @simplewebauthn/server 14.0.3 and @simplewebauthn/browser 14.0.0 are its passkey gate.

## How it is built and run

```
bun install
bun run typecheck
bun run lint
bun run test
bun run build
bun link
canopy ui ~/dev
```

- Development: `bun run dev` (API on :7850) and `bun run dev:web` (Vite on :7851, proxying `/api`).
- Production: the Bun server on :7850 serves the built `dist/web` (the page, `sw.js`, `manifest.webmanifest` and `icons/`), so a stale build shows a stale UI.
- Shared backend: docker compose (`canopy`, `shells`, `stages`, `coord` (the coordinator's runner, always up, used only once `.env` sets `CANOPY_COORD_SOCKET`, `CANOPY_COORD_API` and `CANOPY_COORD_PORT` and canopy enforces caller tokens, its lane held on that port's own listener), `coord-proxy` (the coordinator's egress proxy, its one way to the internet, which tunnels to Anthropic's names alone), `secrets`, and `tunnel` under its profile). Deploy committed `main` with `bun run redeploy`; `bun run redeploy status` says what is running. From the Mac it goes to the mini unless a backend is named (`desoto`, or `all`); `bun run redeploy mac` updates the Mac's own server through a key that runs only `scripts/mac-update` there. See `docs/deploy.md`.
- Run `bun test` with `SHELL=/bin/bash` when an interactive zsh config slows shells down.
- Run the whole suite as `bun run test`: the script passes `--timeout 20000`. Bun applies the preload's `setDefaultTimeout` to the first test file only, so a bare `bun test` runs every later file at Bun's 5 s limit, which the tests that start a server or clone a repo go over when the machine is busy.

Which side question shows beside which run is page state, gone on a reload.

On the mini the `secrets-data` volume holds the checkout, the keys, `passkeys.json`, `audit.jsonl`, `applied.json` and `proposals.json` (what waits for an approval, still sealed). On every other backend, next to the config: `secrets/` (a pulled copy), `secrets-config.json` (the pinned key and remote), `secrets-key.age` (that machine's passphrase-wrapped key) and `secrets-applied.json`. On the mini the backend runs `claude plugin` with `HOME` at `CANOPY_HOST_HOME`, so the paths claude records are the host's. canopy keeps a machine's catalog in memory for 10 minutes and nothing on disk. Which agents it manages is `plugins` in the kit's `~/.claude/kit.json`, and the machine that commits dotclaude's shared `settings.json` is `machines.<name>.commits`.
- A coordinator's card is `propose`, `ask` or `project`. A project card has no repo (it stores `~goal`), holds a `sprout` id instead of a run, and is started in process through the incubator's intake with `via: "coordinator"`; the card follows the sprout and settles when it is live, handed off, rejected, stopped or dismissed. The kept run record carries `action`, `repo` and `sprout` for it.
- A repo's map (FR-070) is the repo's own `floorplan/`, which a map run writes and which keeps itself out of git with a `.gitignore` of `*`. Its `.cache/server.json` holds the map server's pid, port and token. `floorplan/bin/node` in the config dir is the link to bun, made only on a machine with no node.
- A repo's diagrams (FR-071) are the repo's own `.archify/<type>-<slug>-<time>/` folders, each holding a candidate JSON, the page and Archify's receipts, which a diagram run writes. `.archify/.gitignore` of `*` keeps them out of git unless the repo already tracks the folder. The map section's choice of kind is per browser, in localStorage.
- A repo's Architecture Diagnosis (FR-075) is the repo's own `.archify/diagnosis/`: `analysis/` as Archify's Code Analysis wrote it (the page `repo.analysis.html`, `overview.json`, `findings.json` and the graphs, less `raw-facts.json`, which canopy removes after a run along with the run before), `canopy-config.json`, the excludes canopy gave that run, and a `.gitignore` of `*`. Which analyses are going and why the last one failed sit in server memory.
- A repo's reserved feature numbers (FR-076) are git refs in the repo, `refs/canopy/fr/NNN`, each on a commit with no files whose message holds the title, the session, the branch and the backend. `canopy fr reserve` makes one and pushes it to origin without force. canopy keeps no other record of them.
- A repo's knowledge graph (FR-072) is the repo's own `.ua/` (or `.understand-anything/` where a graph from before upstream's rename is), which a graph run writes, kept out of git by a `.gitignore` of `*` unless the repo tracks it. The prepared plugin is `understand/plugin-<version>-<key>/` in the config dir, keyed by a hash of `lib/understand-anything`. `understand/servers/<hash of the root>.json` holds a viewer's pid, port, token and copy key, beside its log, and `understand/bin/python` links to python3 where a machine has no python.
- A tenant (FR-074, plan 3) is a canopy of its own with its own config dir. On a Mac: `tenants/<name>/` next to the config, holding `tenant.json` (its name, folder, port, host kind and the address the page dials, 0600), `config/` (its `$CANOPY_CONFIG_DIR`), `home/` (its `HOME`) and `server.log`, with its launchd agent at `~/Library/LaunchAgents/canopy.tenant.<name>.plist`. On Linux: `~/.local/share/canopy-tenants/<name>/` on the host, holding `tenant.json`, `.env` (the compose project's, 0600) and `home/` (its `.claude`, `.claude.json`, `.codex` and git config), with its config in the compose volume `canopy-t-<name>_config`. Each is named in the host's `backends`.
- No database of its own: git and the files above are the state.

## Decisions

- 2026-08-03: Shell out to `git` and parse porcelain v2, because the same call then runs locally or over ssh for a remote repo.
- 2026-08-24: Drive the user's own `claude` binary over stream-json, not the Agent SDK, because jobs must run on the user's Max login and settings (the SDK was tried and rolled back).
- 2026-10-26: canopy's MCP server uses the existing line JSON framing and the caller's own API token, because the small stdio protocol needs no SDK or second rights model. The shells image carries a launcher for its bundle on the config volume.
- 2026-08-24: No CSS framework; one stylesheet of `light-dark()` tokens, because themes only flip `color-scheme`.
- 2026-09-11: The devhub library moved into canopy, because one engine and one dashboard beat two copies of the data.
- 2026-09-21: Shells are tmux sessions on canopy's own server, because a shell must outlive a reload and a canopy restart.
- 2026-09-22: Headless shared backend in containers, with shells in a container of their own, because a redeploy must not kill open shells.
- 2026-09-24: Peers sync over git only, pull-only and fast-forward only, because work should move between machines through commits, never file copies.
- 2026-10-09: canopy takes only the doc half of the shared spec and keeps its design system in `ui/src/styles.css`, because its own palettes and tokens predate the shared DESIGN.md and differ from it.
- 2026-10-16: Every API call carries a caller token with rights (read, plan, operate, shell, admin, helper), checked at the top of `route()`, because a bare `curl -X POST` from a run must not be able to start or stop a run. It ships in `log` first, then `enforce`.
- 2026-10-14: Secrets live in one signed, age-sealed file in Forgejo, written only by a service on the mini behind passkeys, because a value must never sit in a container that shares the shells' namespaces or in a repo canopy syncs.

## Out of scope

- Hosting git or replacing GitHub or Forgejo; canopy reads them.
- Passwords, email or SSO for people, per-repo roles, and a wall between teams on one backend that holds against a member's own agent or shell. People sign in with an invite or an approved device (FR-074), and groups that must not read each other's files get a backend each.
- Calling the Anthropic API directly or storing API keys for Claude.
- Running a cloned third-party repo's tasks on its own.
