# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

canopy — multi-repo git cockpit (Bun + TS server, React 19 + Vite SPA, full CLI). See README.md for commands and features.

## Commands

- Gates: `bun run typecheck && bun run lint && bun test && bun run build` — all four before calling anything done. Build is required: the server serves `dist/web`, so a stale build shows stale UI.
- Single test file: `bun test src/core/git.test.ts`
- Dev: `bun run dev` (API :7850) + `bun run dev:web` (Vite :7851, proxies /api). Production mode is the built SPA served by the Bun server on :7850 only.
- Shared-backend mode (see `docs/prd-shared-backend.md`, `docs/deploy.md`): canopy can run headless in a container (`Dockerfile`, `docker-compose.yml`; the port is published on the host's tailnet address from `.env`, and `docker-compose.sidecar.yml` adds a tailscale sidecar for a host that is not on the tailnet) as one always-on backend for every client on the tailnet; the tmux server that holds the shells runs in a second container, the `shells` service, off the Dockerfile's `shells` stage (runtime, user, claude, codex, `lib/tmux.conf`, no canopy code, so a canopy rebuild does not move its image and compose leaves it running) as `tmux -S /config/tmux.sock -f /app/lib/tmux-server.conf -D` (foreground; that conf sources the shared one and sets `exit-empty off`), with every mount canopy has since the shells run there, a `list-sessions` healthcheck that canopy's `depends_on` waits for (a `new-session` before the socket exists would start a server inside the canopy container, gone with it), which is what makes a canopy redeploy or crash keep every shell (Phase 4; a host reboot still ends them, by decision); it runs on the mini since 2026-09-22, as the host user (`bun`, uid remapped by build args) because claude refuses `--dangerously-skip-permissions` as root, with `SHELL=/bin/bash` since `userShell()` falls back to bash off a Mac and a missing shell kills every tmux session at birth. `hostOpeners()`/`backendCaps()` in `core/openers.ts` put a `Backend` (`openers`, `sshHost`) on `ScanResult`: when the host is not a mac desktop the server refuses the launcher with `NO_DESKTOP` and the UI hides the launch section. The desktop openers follow the client instead, through a helper: `canopy helper --backend URL` (`core/helperd.ts`, Bun-only: dials `GET /api/helper?name=&platform=&openers=` as a websocket, reconnects at doubling waits, runs each intent through `openIn`/`openFile`/`openGroup` here and answers under its id; `localOpeners` finds what is installed through `helperOpeners`; both ends ping every `HELPER_PING` (20s) and give up after `HELPER_DEAD` (60s) of silence, since a backend that dies with its host sends no close frame and the socket would sit half-open forever, the helper believing it is registered and the server offering one that is gone (`staleHelpers` is the sweep, `retire` the helper's own side)) speaks the pure protocol in `core/helper.ts` (`parseHelperQuery`, `parseHelperIntent`, `parseHelperReply`, `reachFrom` which rewrites a backend-local path to `ssh://$CANOPY_SSH_HOST<path>` for the helper, `parseDefaultGateway` off `/proc/net/route`). The server keeps `state.helpers` by name (a newer one under a name replaces the older), lists them at `GET /api/helpers`, broadcasts the list as a `helpers` event on attach and detach, and answers `GET /api/client` with a `ClientInfo` (`address`, `local` = loopback on a mac desktop, `shared` = the address is the container's default gateway, which is what docker's userland proxy hands it for every client, so it tells no browser apart); the open routes (`repos/open`, `repos/openfile`, `workspaces/open`) take `helper` in the body and relay through `askHelper` (`HELPER_TIMEOUT` 20s then 504, a helper's error is a 502), or run on the backend's own desktop for a loopback browser on a mac, else 400 `NO_HELPER`. The browser derives what it can open through the pure, browser-safe `clientCaps` in `core/client.ts` (its `helper` setting first, the one helper at its own address when the address is not shared or loopback, `local` next, else nothing; the arrays it returns are stable references so a `useShallow` selector over it settles) as `capsFor(s)` in the store, and `helperFor(s)` is the name every open call sends; `RepoMenu` gates agent, herdr and the "open in" row by those openers and shows the VS Code `vscode-remote://ssh-remote+$CANOPY_SSH_HOST` link when there is no `code` among them, the workspace buttons in `TopBar` do the same, and `Settings` has the picker ("desktop openers", `auto` or a helper by name) with the address the browser is seen as. Presence (Phase 3) is by browser, not by address, since the proxy collapses them: each browser profile mints a 16-hex id once (`clientId()` in `ui/src/client.ts`, localStorage `canopy.client`) and names itself from the `device` setting or the user agent (`deviceName`/`platformOf` in `core/presence.ts`, browser-safe), and `identity()` puts `client`, `name` and `platform` on the event stream's query and `client` on every shell socket's; the server keeps `state.streams` by SSE controller (`parseStream` validates the query; a stream without a client is no device), folds them into `Device[]` through `devicesOf` (one per id, newest name, oldest `since`, `streams` count) for `GET /api/devices` and the `devices` event (`tellDevices`, debounced 300ms), and `termInfo` adds `viewers` (device names with a socket on the shell) to every `TermInfo`, broadcast whole as a `terms` event by `tellTerms` on every start, join, leave and end; a run keeps `by` (the starting browser's device name, from `client` in the run request) and `RunSheet` shows it. The store holds `devices` and `shells` (the live `TermInfo[]`), `KeptShells.tsx` is the top bar's `⟲ n` chip and popover, there only when a machine going down left shells behind: one row each (repo, how long ago, lines, the agent it had) with restore, "restore + continue" for a claude shell, and forget, while the switch itself is a row in `Settings` since it is the backend's setting and not this browser's; `Devices.tsx` is the top bar's `⌘ n` chip and popover (platform word, `ago()`, windows, this browser, "in a shell at …" off the viewers), and `adoptTerms` in `ui/src/term.ts` (tested) turns every held shell into a tab on the `terms` event and at load, a panel shell only once its panel is open (`openPanel` adopts too), so a shell opened on one device is a tab on every other; the feed reads `helpers`, `devices` and `terms` events into device and shell lines. Presence labels and never authorizes. `openers.ts` has Linux builders next to the macOS ones (`linuxCommandFor`, `linuxRemoteCommandFor`, `linuxAgentArgs`: kitty `--detach`, `xdg-open`, no Terminal.app) and `openIn`/`openAgent`/`openGroup` branch on `process.platform`, so the helper runs on Omarchy too. `CANOPY_NO_DESKTOP=1` forces the headless behaviour on a mac; `CANOPY_SSH_HOST` names the ssh alias for the VS Code link and the helper's locators; `canopy ui --no-open` skips opening a browser. The launcher (`core/launcher.ts`) stays backend-side and macOS-only by design; the in-browser core (shells, runs, git, search, diffs, history) is backend-host and works anywhere.

## Architecture

- `src/core/` — pure logic, no HTTP: host (locators: a repo path is absolute, or `ssh://<host><path>` for another machine; `parseLocator`, shell quoting, the ssh argv with a shared ControlMaster socket per host under the config dir; pure and tested), exec (`onHost(host, cmd)` runs here or over ssh, and `git()` routes by the repo's locator so nothing above it knows where a repo lives), scan (find `.git` dirs, never descend below a repo root except into its checked-out submodules, which `parseGitmodules` reads off `.gitmodules` and which get cards of their own however deep they sit, while a plain clone vendored under a repo stays hidden; `scanSource` takes a `Source` and yields repos with ids `<source id>:<rel>`, bare under the launch root; the remote walk is one `find -L … -print0` mirrored from the local one that also prints every `.gitmodules`, read in a second round trip through `catCommand`, then `withSubmodules` keeps the top-level repos plus their listed submodules down the chain), git (porcelain-v2 parsing, all mutations; `getStatus` also reads the newest remote-tracking commit the checkout does not contain through `tipArgs(remotes?)` (`for-each-ref --no-merged=HEAD` under every remote, or just the ones named; parsed by `parseRemoteTip`, skipping each remote's HEAD symref) into `status.tip`, absent when there is none, and never read when `tipRemotes` is an empty list; `fetchRepo(path, remotes?)` is `git fetch --all` or `--multiple <names>` with `--prune` and `GIT_TERMINAL_PROMPT=0` and reports whether `remoteRefs` changed; `getCommit` reads one commit with `--numstat -z` and `--name-status -z` joined on path, `getDiff` takes a `DiffTarget` union: worktree, untracked, or one commit's change to a file), suggest (claude CLI shellout with heuristic fallback), openers (macOS `open`-based launchers + .code-workspace/kitty-session generation; `agent` runs `claude` through the login interactive shell in a held kitty window, or Terminal via osascript when kitty is missing; every launcher takes the repo's `AgentSettings` and `claudeLine` turns them into the `claude …` shell line; the argv builders are pure and tested), herdr (the `herdr` opener: drives the herdr CLI's socket API to focus the workspace already at a repo's folder or create one and `agent start` Claude in its pane with the settings after `--`; the name/argv builders and the JSON readers are pure and tested, `openHerdr` is Bun), agent (browser-safe: `normalizeAgent` validates settings field by field, `claudeArgs` makes the flags, `splitArgs` reads the extra-flags box like a shell, `describeAgent` is the menu's one line), github (`PULLS_QUERY` is the one GraphQL query over every repo the gh login can see with its open PR count, `parsePullCounts` reads `gh api graphql --paginate --slurp` output into a map by lowercased slug, `githubSlug`/`pullsFor`/`linkPulls` join it onto repos by remote url; pure and tested), access (`ownRemote(url, deps)` decides which remotes the server fetches in the background, self-hosted per `isSelfHosted` (no public forge) or a GitHub remote `accessFromUrls` says is pushable, and `ownRemotes` names a repo's own ones in config order; `pushAccess` is the same judgement over a repo path's remotes), forge (a self-hosted Forgejo through its API: `apiBase` normalizes the address it was added as, `listForgeRepos` pages `/api/v1/user/repos` with a token read from a file or `$CANOPY_FORGEJO_TOKEN`, `forgeRepo` turns one API repo into a card with `status: null` and the forge's page as its `path`, `linkForgeClones` matches those cards to local clones by remote url and hands a clone the forge's page when it has no link of its own; everything but the fetch is pure and tested), meta (what a card says beyond git state: the remote as a web URL via `webUrl` in access.ts, and a one-line description from package.json/Cargo.toml/pyproject.toml, else the README's first prose line; read at scan time only, so a file event does not re-read it), store (config at `~/.config/canopy`, overridable via `$CANOPY_CONFIG_DIR` — tests rely on this; `sources` are the extra scanned folders, `addSource`/`removeSource`, ids slugged from labels and unique; `agents` are the per-repo agent settings keyed by repo path, `setAgent` drops an entry set back to the defaults, `agentFor` reads one), actions (browser-safe: labels, preconditions, and prompts for the Claude-driven actions; `chat` is the conversation, whose prompt keeps the safety rules and puts the first message last; tested), runner (Bun-only: spawns the `claude` binary per run with stream-json on both ends and the repo's agent settings as flags (yolo → `--permission-mode bypassPermissions`), folds its messages into a plain `Run`, parks on permission/question prompts until `answer()`; a chat run keeps stdin open after each `result`, goes `idle`, and `say()` sends the next user message down the same process (the first message spawns it); `stop()` on an idle chat closes stdin so the CLI exits and the chat is `done`; on end, re-reads status and sets `outcome` changed/unchanged via `statusFingerprint`), term (a shell inside canopy: `shellArgs` is the login interactive shell for a folder here or `sshSessionArgs` for one elsewhere, `termSize` clamps what the browser asks for, `parseTermMessage` reads the one text frame it sends, `isTermId` checks the 32-hex name the browser gives a shell, `Scrollback` is the capped ring of what a pty wrote for the next socket to see, all pure and tested; `spawnOnPty` and `startTerm` are Bun-only, a `Bun.Terminal` pty with a command (the shell) spawned on it, and a plain pty outlives the socket: the server holds it by name until it exits, the tab's × ends it, or the server stops), tmux (the shell that outlives the server: one session per shell named `canopy-<id>` on a tmux server of canopy's own, socket `tmux.sock` under the config dir, started with `lib/tmux.conf` (status off, `prefix None`, `smcup@:rmcup@` so it draws on xterm's normal screen and scrollback works, `exit-empty on` so the tmux server goes with its last session); the repo, place and path ride as `@canopy_*` user options set in the same `new-session` call, `LIST_FORMAT`/`parseSessions` read them back, `primeText` turns a `capture-pane` of the history into terminal lines pushed off a screen of `rows` so they land in scrollback ahead of tmux's first draw; the argv builders, the parser and `primeText` are pure and tested, `tmuxBase()` is null under `CANOPY_TMUX=0` or without tmux on PATH, and `attachTmuxTerm` is one pty client per socket through `spawnOnPty`, so tmux hands each browser the screen and modes and its terminal queries are answered live; `newSession` runs `shellArgs` (an ssh line for a remote repo, so the other host needs no tmux); tests in `tmux.test.ts` and the integration in `server/term.test.ts`), keep (what a shell leaves behind, so a reboot does not take it with the tmux server: while config `keepShells` is on, the server snapshots every held shell every `KEEP_EVERY` (60s) through `snapshotArgs` (`capture-pane` over the history *and* the visible screen, which `captureArgs` leaves out since an attach redraws it and a reboot does not), `clip`s it to `KEEP_LINES`/`KEEP_BYTES` and writes a 0600 record plus history per shell under `shells/` in the config dir, the volume the shells container shares; `lostShells` is the records no live session answers for, `expiredShells` drops one `KEEP_DAYS` (7) after it was written, `agentIn(command, title)` tells what was running off what tmux reports (measured: Claude Code's process title is its own version, `2.1.278`, and its pane title starts `claude`, codex reports `codex`, a plain shell reports the shell, which is what keeps a shell in a folder called `claude-history` from looking like an agent), `continueLine` is the `claude --continue` a restore can type in, `restoredBanner` is the line ahead of a restored shell's history; all but the four fs calls pure and tested), search (`grepArgs` is the `git grep -n -I --column -z -i -F -e … --` argv, `parseGrep` reads its `path\0line\0col\0text` records, drops leading indentation, clips a long line around the match through `clipLine`, and stops at `GREP_LIMIT` with `truncated`; `searchRepo` runs it through `git()` so a remote repo works the same and treats exit 1 as no match; `mapPool` is the bounded fan-out; all but `searchRepo` pure and tested), history (Bun-only: shells out to the claude-history CLI with `--json`; `historyOverview` matches repos to archive projects by realpath and folds `activity` into per-day arrays for the rings; `localDays`/`localMidnightIso` are pure and tested), workflow (browser-safe, pure and tested: `parseWorkflow(text, source) -> Workflow | { error }` reads a workflow markdown file's frontmatter and `##` steps into a `Workflow`), workflows (Bun-only: `loadWorkflows(repo)` reads the three sources — `lib/workflows/*.md` bundled with canopy, `$CANOPY_CONFIG_DIR/workflows/*.md`, and `<repo>/.canopy/workflows/*.md` for a local repo — and merges them by `name`, later sources winning, including the broken ones with their `error`; re-read on every request, no watcher, `findWorkflow` looks one up by name among the ok ones), flow (class `Flows`: the orchestrator over Runner, one Run per workflow step through the pure `stepSpec`, built against a small `FlowRunner` interface so tests use a fake and the server is the only caller that wires in the real Runner; after a step's Run ends it runs the step's `check` through `onHost`, then the gate — continue, ask, or verdict through an injected evaluator hook — and `resume()` continues, retries or stops a gated flow; fleets run one workflow over many repos at `FLEET_CONCURRENCY` (3) at a time, skipping any repo `fleetSkipReason` flags as not meeting the workflow's `when`), verdict (browser-safe, pure and tested: `VERDICT_QUESTIONS` the evaluator is asked, `decide(answers)` turns them into a go/park `Verdict` against the thresholds in `THRESHOLDS`, `verdictState` builds the text the evaluator reads from a step's summary, check output and whether status changed), launch (browser-safe, pure and tested: `normalizeLaunch`/`isDefaultLaunch`/`describeLaunch` for the four per-repo lines, `pickAsset(names, platform, glob)` picks the release asset for this machine, `parseReleases`/`parsePulls` read GitHub's API shapes, `unpackKind` and `launchTarget` say what a download turns into and what to run out of it, `buildKey`/`parseBuildKey` name a build `release:<tag>`, `pr:<n>` or `local`), launcher (Bun-only: class `Launcher`, the generic take on freecad-launcher: `releases`/`pulls` through `gh api`, `install` downloads an asset into `$CANOPY_CONFIG_DIR/builds/<owner>/<name>/release/<tag>/` and unpacks it (dmg via hdiutil, zip via ditto, tar), `build` fetches `pull/<n>/head` into a worktree under `.../pr/<n>/` or builds the checkout itself, both as a `Job` whose output tail broadcasts throttled, `launch` starts a build (an `.app` through `open -n -W`, whose wait is the tracked process while the app itself belongs to launchd, so `stopLaunch` quits it with `pkill -f` on its `Contents/MacOS/` path; a binary directly; a checkout through its run line) and keeps the process so `stopLaunch` can end it and `exited` can be broadcast, `builds` lists what is here with launch counts from the repo dir's `state.json`; hooks `onJob`/`onJobGone`/`onBuilds` are what the server broadcasts; tested against a fixture repo for the local build and launch path, a stub `.app` through `open -W`, and every unpack shape (`unpack` is exported for that)), jev (Bun-only: the evaluator itself, `typesafe-ai/jev` over the Vercel AI Gateway through `@ai-sdk/gateway`, retried on a short timeout; `hasGatewayKey` is true only with `AI_GATEWAY_API_KEY` or `VERCEL_AI_GATEWAY_API_KEY` set, and `flow.ts`'s evaluator hook is `null` without one, so a `verdict` gate behaves like `ask`).
- `src/server/` — Bun.serve: REST + SSE (`/api/events`) + static. State holds one `SourceRuntime` per scanned folder (the launch root first, then config `sources`); `scanOne` swaps a source's repos into the aggregate `result` and `rebuildResult` reorders by source. One recursive `fs.watch` per local source maps changed paths (relative to that source) to the longest-matching repo via `repoRel`, debounces 400ms, re-reads status, broadcasts; ssh sources have no watcher and get their statuses re-read every `REMOTE_REFRESH` (5 min); the same timer, and once `ACTIVITY_DELAY` after start, runs `refreshActivity`: `fetchLocal` fetches every local repo's own remotes (`ownRemotesOf`, memoized per path in `state.own` over `listRemotes` and `ownRemotes`), `FETCH_CONCURRENCY` at a time, skipping a repo with an active run since a fetch would move the fingerprint its outcome is judged by, and calls `scheduleRefresh` (the same 400ms debounce the watcher uses, so the two coalesce) for each repo whose refs moved or whose own remotes were just learned; `scanOpts` hands `scanSource` a `tipRemotes` hook and `refreshAndBroadcast` hands `refreshRepo` the same list, so a status read only ever takes a tip off the user's own remotes and none at all before the first pass has looked; then `refreshPulls` runs `PULLS_QUERY` through gh, keeps the map in `state.pulls`, and broadcasts each repo whose `pulls` changed; `rebuildResult` re-attaches the counts through `linkPulls` so a scan keeps them; config `fetch: false` skips the fetch; a forgejo source is a server rather than a folder, so `scanSource` lists it through the API, it gets no watcher, and the same timer re-lists it. `rebuildResult` runs `linkForgeClones` over the whole tree, since which forge repos are already cloned here can only be told once every source is in one list, and every `/api/repos/*` route answers 400 for a repo with a `forge`: there is no checkout to run git in. Sources: `GET/POST/DELETE /api/sources` (POST validates: local paths must be directories and not overlap an existing local source, ssh hosts must match `isSshHost` and the path is resolved with `cd … && pwd -P` on the host; a 502 means ssh itself failed; a forge is proved by listing its repos, 400 for a bad address or a refused token, 502 for one that will not answer), `POST /api/sources/rescan?id=`, `GET /api/hosts` (aliases from `~/.ssh/config`), `GET /api/browse?path=&host=` (one folder's visible subfolders with a repo flag; local via readdir in `core/browse.ts`, remote as one `sh -c` script that prints `pwd -P` then `r name`/`d name` lines, parsed by `parseBrowse`). `/api/repos/run` answers 400 for a repo with a `host`. Runs: `POST /api/repos/run?id=` starts one, `/api/runs` lists, `/api/runs/answer|stop|say` and `DELETE /api/runs?id=` drive it (`say` is a chat's next message); every change broadcasts the whole `Run` as a `run` event (`run-gone` on dismiss). Agent settings: `GET /api/agents` is the whole map by repo path, `POST /api/repos/agent?id=` stores one repo's (normalized server-side) and broadcasts the map as an `agents` event; `/api/repos/open`, `/api/repos/run` and `/api/workspaces/open` read them. Drill: `GET /api/repos/commit?id=&hash=` (400 for a non-hash, 404 for an unknown one) and `GET /api/repos/diff?id=&file=&commit=&orig=` for one file's diff in that commit. Shells: `GET /api/term?id=&term=&place=&cols=&rows=` upgrades to a websocket (404 unknown repo, 400 forge or a malformed `term`, 426 without an upgrade); `term` is the browser's 32-hex name for the shell: a name the server holds is joined (the `Scrollback` replays first, then the pty takes the socket's size so a full-screen program repaints), any other starts a shell under it, and `attach=1` joins only, closing with `TERM_GONE` (4404) for a name not held; binary frames are keystrokes down and pty output up, a text frame is `{"resize":{"cols","rows"}}` down and `{"exit":code}` up before the close. A socket closing detaches and leaves the shell running (several sockets may sit on one shell, every one gets its output); `state.terms` is the `Map` by name, `GET /api/terms` lists them as `TermInfo` (with `attached`), `DELETE /api/terms?term=` ends one, and stop ends them all. On tmux (`state.tmux`, the argv front, non-null when `tmuxBase()` found it) a `LiveTerm` has `pty: null` and `joinTmuxTerm` does the work: `newSession` for a name not held, `TERM_GONE` for a held name whose session died, then `history` sent as the first frame, then the socket's own client (`ws.data.client`) attached to the session, which `close(ws)` detaches; a client exiting while the session lives (a `tmux detach` inside) closes the socket with no exit frame so the browser rejoins with a new client, and one exiting with the session sends `{exit}` and drops the entry. `listTerms` reconciles the `Map` with `listSessions` on every list and at startup, which is how a restarted server finds the shells the last one left; `endTerm` is `kill-session`. Shells kept across a reboot (Phase 4): `GET /api/terms/kept` is `{ keeping, kept }` (the config switch and the `KeptShell[]` no live session answers for), `POST /api/terms/restore` `{term, cols, rows, resume}` starts one again **under the same id**, so every saved tab and `?term=` url comes back to it, with the old history and `restoredBanner` sent ahead of the session's own through `history(..., ahead)` and dropped once `historySize` says the new session has scrolled a screen of its own, and `resume` types `continueLine` in after a beat (404 for a name nothing was kept under, 409 for one that is running, 400 for a repo that left the scan); `DELETE /api/terms/kept?term=` forgets one, `POST /api/keep {on}` writes the config switch and takes a first pass; the snapshot timer is `KEEP_EVERY` and `keepPass` never stacks two; a `kept` event carries the list to every browser, and ending a shell forgets its record. A session that is gone when a client exits is only a shell that exited when `serverUp` says canopy's tmux server is still answering: the shells container restarting under a live canopy kills every client at once, and forgetting the records there would throw away exactly what the restart is supposed to leave behind. `canopy ui --no-open` starts the server without opening a browser tab (a launchd-restarted server otherwise opens one per restart, each a window on the same shells). Search: `GET /api/repos/grep?id=&q=` is one repo, `POST /api/grep {q, ids}` is many (one `GrepRepoResult` per id in the order given, `GREP_CONCURRENCY` at a time, a failed repo carries `error` instead of failing the call); `grepQuery` refuses an empty, multi-line or over-long term with 400. `POST /api/repos/openfile?id=` `{file, line}` opens the file in VS Code through `openFile` in openers (`fileOpenArgs` is pure: `code -g path:line`, behind `--remote ssh-remote+host` for a remote repo). History: `GET /api/history` (the overview, memoized 5 min and per scan; `?refresh=1` forces), `GET /api/repos/sessions|session|search?id=` and `POST /api/repos/note?id=` (opens the vault note); all answer 503 with the reason when the CLI is missing and 404 when the repo has no project in the archive. Workflows and flows: `GET /api/repos/workflows?id=` is one repo's list (ok and broken entries both); `GET /api/verdict` is `{ ready: hasGatewayKey() }`, what the UI reads to know whether a `verdict` gate can evaluate or will fall back to `ask`; `POST /api/repos/run?id=` with `action=flow` starts a flow for one repo (400 for a `host` repo — flows are local-only — and for an unknown or broken workflow name); `GET /api/flows` lists every flow, `DELETE /api/flows?id=` dismisses one, `POST /api/flows/resume` (`{id, choice}`, `continue|retry|stop`) and `POST /api/flows/stop` drive a gated or running one. Fleets: `GET /api/fleets` lists them, `POST /api/fleet` (`{workflow, ids, note}`) starts one over several repos found in `state.result.repos`, `POST /api/fleet/stop` and `DELETE /api/fleet?id=` drive and dismiss one. Every change broadcasts as one of four events: `flow`, `flow-gone`, `fleet`, `fleet-gone`, the whole Flow or Fleet each time (a flow's own step Runs still broadcast as `run`, so the console component needs no flow-awareness). Launcher: `GET /api/repos/releases|pulls|builds?id=`, `POST /api/repos/install?id=` `{tag, asset?}` and `POST /api/repos/build?id=` `{pr?}` each answer 201 with a `Job`, `POST /api/repos/launch?id=` `{build}` answers the `Build` after the launch, `halt` ends its process, `uninstall` removes it, `launcher` stores the repo's `LaunchSettings` and broadcasts the map as `launchers`; `GET /api/launchers`, `GET /api/jobs`, `POST /api/jobs/stop`, `DELETE /api/jobs?id=`. Jobs broadcast as `job`/`job-gone`; a `builds` event names the repo whose builds changed outside a job (launched, exited, removed) or that a job just installed or built one, and the panel re-reads the list on it. A `LauncherError` carries its own HTTP status. Releases work for any repo with a GitHub remote, wherever its checkout is (the download lands here); builds are local-only.

## Conventions & gotchas

- `git status --porcelain=v2` paths are never quoted; fields split on single spaces with the path last (`splitN`). Rename entries carry `path\torig`.
- Untracked-file diffs use `git diff --no-index /dev/null <file>`, which exits 1 on success — don't treat that as an error.
- `unpack` attaches a dmg through a hard link without the `.dmg` extension (`Stub.image`), `-nobrowse` on a private mountpoint, and retries with `-imagekey diskimage-class=CRawDiskImage` when hdiutil says "image not recognized" (a raw image is only told apart by its extension). The link is what keeps "Install this app?" helpers quiet: Vorssaint's disk image installer on this Mac sees every mount, even `-nobrowse` ones, and offers to install the one app on any mount whose `hdiutil info` image path ends in `.dmg`. The launcher tests build their fixture image mount-free (`makehybrid`, then `convert` to UDZO) for the same reason, and unregister the stub app bundle the `open -W` test hands to Launch Services, since the entry outlives the scratch dir.
- Remote repos assume a POSIX shell, key-based login, and git on the non-interactive PATH of the host (the QNAP has no git, so it can be added but every card there errors). `remoteCommand` single-quotes each argv word; `tildeQuote` keeps a leading `~` bare so the remote expands it. Openers for a remote path run `ssh -t host 'cd … && …'` (kitty, Terminal, agent) or `code --folder-uri vscode-remote://ssh-remote+host/path`; Finder throws.
- SSE clients buffered through some proxies/sandboxes may look silent; verify reactivity in a real browser before debugging the watcher (the watcher path was correct all along the one time this came up).
- Runs deliberately do not use `@anthropic-ai/claude-agent-sdk` (it was tried and rolled back): jobs must run on the user's own `claude` install and Max login. The runner spawns `claude -p --input-format stream-json --output-format stream-json --permission-prompt-tool stdio`; the prompt goes down stdin as a `user` message, permission requests come back as `control_request` (`subtype: can_use_tool`) and are answered with a `control_response` carrying `{behavior, updatedInput}`. `AskUserQuestion` arrives the same way and is answered by returning `updatedInput.answers`. Stdin must stay open until the `result` message (the CLI exits once it is closed); a chat keeps it open past the result and writes the next `user` message to continue the session. `--setting-sources user,project,local` so CLAUDE.md and permission rules apply; MCP servers are off (`--strict-mcp-config` with no `--mcp-config`).
- claude-history's `--json` shapes are passed through as-is (snake_case types in `types.ts`); its README calls them an API for canopy's sake, so change both sides together. Its CLI answers a bad lookup as plain text with exit 0; `report()` in history.ts turns that into a 404. Days are local: the CLI buckets with sqlite `localtime` and canopy builds the day list with the OS clock, which agree in the server but not under `bun test` (Bun pins JS Dates to UTC there), so tests pass explicit dates.
- Design system lives entirely in `ui/src/styles.css` (bark/moss/lichen/rust/sky tokens as `light-dark()` pairs; the theme setting only flips `color-scheme` via `data-theme` on `<html>`). No CSS framework — keep it that way.
- A fleet resolves its workflow once, from the bundled and user sources only (not a repo's own `.canopy/workflows/`), since a fleet runs the same file over every repo it touches and a repo-local override would make that not true. `loadWorkflows` skips the repo source whenever `repo.host` is truthy (it assumes a remote repo, no local `.canopy/`), so the server asks with `loadWorkflows({ path: "", host: "none" })` — a fake host, not a fake path, is what actually suppresses it.
