# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

canopy — multi-repo git cockpit (Bun + TS server, React 19 + Vite SPA, full CLI). See README.md for commands and features.

## Commands

- Gates: `bun run typecheck && bun run lint && bun test && bun run build` — all four before calling anything done. Build is required: the server serves `dist/web`, so a stale build shows stale UI.
- Redeploy the mini's shared backend: `bun run redeploy` (`status`, `log`, `--pull`, `--shells`), from the Mac, a canopy shell on the mini, or the mini itself; `scripts/redeploy.sh`, the `redeploy` skill, and `docs/deploy.md`.
- Single test file: `bun test src/core/git.test.ts`
- Dev: `bun run dev` (API :7850) + `bun run dev:web` (Vite :7851, proxies /api). Production mode is the built SPA served by the Bun server on :7850 only.
- Shared-backend mode (see `docs/prd-shared-backend.md`, `docs/deploy.md`): canopy can run headless in a container (`Dockerfile`, `docker-compose.yml`; the port is published on the host's tailnet address from `.env`, and `docker-compose.sidecar.yml` adds a tailscale sidecar for a host that is not on the tailnet; the `tunnel` service, under the compose profile `tunnel` that `.env` turns on with `COMPOSE_PROFILES=tunnel`, is cloudflared with `TUNNEL_TOKEN` for the public name, its ingress `http://canopy:7850` kept in the Zero Trust dashboard, `CANOPY_PUBLIC_ORIGIN` passed to canopy for the origin gate, and Cloudflare Access the only auth in front; `TUNNEL_TOKEN` defaults empty rather than `:?` since compose interpolates profiled services too) as one always-on backend for every client on the tailnet; the tmux server that holds the shells runs in a second container, the `shells` service, off the Dockerfile's `shells` stage (runtime, user, claude, codex, `lib/tmux.conf`, ble.sh and a `~/.bashrc` that sources `shell/bashrc` off the mounted `~/.claude` when the host keeps one, no canopy code, so a canopy rebuild does not move its image and compose leaves it running) as `tmux -S /config/tmux.sock -f /app/lib/tmux-server.conf -D` (foreground; that conf sources the shared one and sets `exit-empty off`), with every mount canopy has since the shells run there (all but the read-only `~/.config/git` one, which only peer sync's wip snapshots read and which would recreate this container, ending every shell, if added), a `list-sessions` healthcheck that canopy's `depends_on` waits for (a `new-session` before the socket exists would start a server inside the canopy container, gone with it), which is what makes a canopy redeploy or crash keep every shell (Phase 4; a host reboot ends the tmux server, and `keepShells` is what brings each shell's terminal and history back after one, not the processes); it runs on the mini since 2026-09-22, as the host user (`bun`, uid remapped by build args) because claude refuses `--dangerously-skip-permissions` as root, with `SHELL=/bin/bash` since `userShell()` falls back to bash off a Mac and a missing shell kills every tmux session at birth. `hostOpeners()`/`backendCaps()` in `core/openers.ts` put a `Backend` (`openers`, `sshHost`) on `ScanResult`: when the host is not a mac desktop the server refuses the launcher with `NO_DESKTOP` and the UI hides the launch section. The desktop openers follow the client instead, through a helper: `canopy helper --backend URL` (`core/helperd.ts`, Bun-only: dials `GET /api/helper?name=&platform=&openers=` as a websocket, reconnects at doubling waits, runs each intent through `openIn`/`openFile`/`openGroup` here and answers under its id; `localOpeners` finds what is installed through `helperOpeners`; both ends ping every `HELPER_PING` (20s) and give up after `HELPER_DEAD` (60s) of silence, since a backend that dies with its host sends no close frame and the socket would sit half-open forever, the helper believing it is registered and the server offering one that is gone (`staleHelpers` is the sweep, `retire` the helper's own side)) speaks the pure protocol in `core/helper.ts` (`parseHelperQuery`, `parseHelperIntent`, `parseHelperReply`, `reachFrom` which rewrites a backend-local path to `ssh://$CANOPY_SSH_HOST<path>` for the helper, `parseDefaultGateway` off `/proc/net/route`). The server keeps `state.helpers` by name (a newer one under a name replaces the older), lists them at `GET /api/helpers`, broadcasts the list as a `helpers` event on attach and detach, and answers `GET /api/client` with a `ClientInfo` (`address`, `local` = loopback on a mac desktop, `shared` = the address is the container's default gateway, which is what docker's userland proxy hands it for every client, so it tells no browser apart); the open routes (`repos/open`, `repos/openfile`, `workspaces/open`) take `helper` in the body and relay through `askHelper` (`HELPER_TIMEOUT` 20s then 504, a helper's error is a 502), or run on the backend's own desktop for a loopback browser on a mac, else 400 `NO_HELPER`. The browser derives what it can open through the pure, browser-safe `clientCaps` in `core/client.ts` (its `helper` setting first, the one helper at its own address when the address is not shared or loopback, `local` next, else nothing; the arrays it returns are stable references so a `useShallow` selector over it settles) as `capsFor(s)` in the store, and `helperFor(s)` is the name every open call sends; `RepoMenu` gates agent, herdr and the "open in" row by those openers and shows the VS Code `vscode-remote://ssh-remote+$CANOPY_SSH_HOST` link when there is no `code` among them, the workspace buttons in `TopBar` do the same, and `Settings` has the picker ("desktop openers", `auto` or a helper by name) with the address the browser is seen as. Presence (Phase 3) is by browser, not by address, since the proxy collapses them: each browser profile mints a 16-hex id once (`clientId()` in `ui/src/client.ts`, localStorage `canopy.client`) and names itself from the `device` setting or the user agent (`deviceName`/`platformOf` in `core/presence.ts`, browser-safe), and `identity()` puts `client`, `name` and `platform` on the event stream's query and `client` on every shell socket's; the server keeps `state.streams` by SSE controller (`parseStream` validates the query; a stream without a client is no device), folds them into `Device[]` through `devicesOf` (one per id, newest name, oldest `since`, `streams` count) for `GET /api/devices` and the `devices` event (`tellDevices`, debounced 300ms), and `termInfo` adds `viewers` (device names with a socket on the shell) to every `TermInfo`, broadcast whole as a `terms` event by `tellTerms` on every start, join, leave and end; a run keeps `by` (the starting browser's device name, from `client` in the run request) and `RunSheet` shows it. The store holds `devices` and `shells` (the live `TermInfo[]`), `KeptShells.tsx` is the top bar's `⟲ n` chip and popover, there only when a machine going down left shells behind: one row each (repo, how long ago, lines, the agent it had) with restore, "restore + continue" for a claude shell, and forget, while the switch itself is a row in `Settings` since it is the backend's setting and not this browser's; `Shells.tsx` is the top bar's `▸_ n` chip, the shells picker: every held shell (`shells`) with join (`joinTerm`: its tab here, or a new one onto it, its panel opened for a panel shell; a dockless window goes to the shell's own `view=shell&term=` url instead), hide here (`hideTerm`: the tab goes without ending the shell, and the name joins `hiddenTerms`, persisted in the layout, which `reconcileTerms` and `adoptTerms` pass over and `pruneHidden` trims to the live shells) and end; and a repo's Claude Code conversations through `GET /api/repos/resumable?id=` (`core/sessions.ts`: `claudeSessions` reads `$CLAUDE_CONFIG_DIR` or `~/.claude` `/projects/<projectFolder(path)>/*.jsonl`, newest first, the first typed prompt, summary and branch off each file's head through the pure `parseSessionHead`; empty for a `host` repo), where resume is `POST /api/repos/resume?id=` `{term, place, session, cols, rows}` (`resumeTerm`: 400 for a bad name or id or a `host` repo, 404 for a conversation not filed under that repo, 409 for a name in use; starts a shell under the browser's name on tmux or a plain pty and types `resumeLine`, `claude <agent flags> --resume <id>`, in after a beat) and the store's `resumeClaude` adds the tab; tests in `sessions.test.ts` and `server/resume.test.ts`; `Devices.tsx` is the top bar's `⌘ n` chip and popover (platform word, `ago()`, windows, this browser, "in a shell at …" off the viewers), and `adoptTerms` in `ui/src/term.ts` (tested) turns every held shell into a tab on the `terms` event and at load, a panel shell only once its panel is open (`openPanel` adopts too), so a shell opened on one device is a tab on every other; the feed reads `helpers`, `devices` and `terms` events into device and shell lines. Presence labels and never authorizes. `openers.ts` has Linux builders next to the macOS ones (`linuxCommandFor`, `linuxRemoteCommandFor`, `linuxAgentArgs`: kitty `--detach`, `xdg-open`, no Terminal.app) and `openIn`/`openAgent`/`openGroup` branch on `process.platform`, so the helper runs on Omarchy too. `CANOPY_NO_DESKTOP=1` forces the headless behaviour on a mac; `CANOPY_SSH_HOST` names the ssh alias for the VS Code link and the helper's locators; `canopy ui --no-open` skips opening a browser. The launcher (`core/launcher.ts`) stays backend-side and macOS-only by design; the in-browser core (shells, runs, git, search, diffs, history) is backend-host and works anywhere.

## Architecture

- `src/core/` — pure logic, no HTTP: host (locators: a repo path is absolute, or `ssh://<host><path>` for another machine; `parseLocator`, shell quoting, the ssh argv with a shared ControlMaster socket per host under the config dir; `scanSource` takes a `Source` and yields repos with ids `<source id>:<rel>`, bare under the launch root; the remote walk is one `find -L … -print0` mirrored from the local one that also prints every `.gitmodules`, read in a second round trip through `catCommand`, then `withSubmodules` keeps the top-level repos plus their listed submodules down the chain), git (porcelain-v2 parsing, all mutations; `getStatus` also reads the newest remote-tracking commit the checkout does not contain through `tipArgs(remotes?)` (`for-each-ref --no-merged=HEAD` under every remote, or just the ones named; parsed by `parseRemoteTip`, skipping each remote's HEAD symref) into `status.tip`, absent when there is none, and never read when `tipRemotes` is an empty list; integration tests wire peers by plain path, which `git` treats as a remote the same as ssh.
- `src/server/` — Bun.serve: REST + SSE (`/api/events`) + static. State holds one `SourceRuntime` per scanned folder (the launch root first, then config `sources`); `scanOne` swaps a source's repos into the aggregate `result` and `rebuildResult` reorders by source. One recursive `fs.watch` per local source maps changed paths (relative to that source) to the longest-matching repo via `repoRel`, debounces 400ms, re-reads status, broadcasts; ssh sources have no watcher and get their statuses re-read every `REMOTE_REFRESH` (5 min); the same timer, and once `ACTIVITY_DELAY` after start, runs `refreshActivity`: `fetchLocal` fetches every local repo's own remotes (`ownRemotesOf`, memoized per path in `state.own` over `listRemotes` and `ownRemotes`), `FETCH_CONCURRENCY` at a time, skipping a repo with an active run since a fetch would move the fingerprint its outcome is judged by, and calls `scheduleRefresh` (the same 400ms debounce the watcher uses, so the two coalesce) for each repo whose refs moved or whose own remotes were just learned; `scanOpts` hands `scanSource` a `tipRemotes` hook and `refreshAndBroadcast` hands `refreshRepo` the same list, so a status read only ever takes a tip off the user's own remotes and none at all before the first pass has looked; then `refreshPulls` runs `PULLS_QUERY` through gh, keeps the map in `state.pulls`, and broadcasts each repo whose `pulls` changed; `rebuildResult` re-attaches the counts through `linkPulls` so a scan keeps them; config `fetch: false` skips the fetch; a forgejo source is a server rather than a folder, so `scanSource` lists it through the API, it gets no watcher, and the same timer re-lists it. `rebuildResult` runs `linkForgeClones` over the whole tree, since which forge repos are already cloned here can only be told once every source is in one list, and every `/api/repos/*` route answers 400 for a repo with a `forge`: there is no checkout to run git in. ## Conventions & gotchas

- `git status --porcelain=v2` paths are never quoted; fields split on single spaces with the path last (`splitN`). Rename entries carry `path\torig`.
- Untracked-file diffs use `git diff --no-index /dev/null <file>`, which exits 1 on success — don't treat that as an error.
- `unpack` attaches a dmg through a hard link without the `.dmg` extension (`Stub.image`), `-nobrowse` on a private mountpoint, and retries with `-imagekey diskimage-class=CRawDiskImage` when hdiutil says "image not recognized" (a raw image is only told apart by its extension). The link is what keeps "Install this app?" helpers quiet: Vorssaint's disk image installer on this Mac sees every mount, even `-nobrowse` ones, and offers to install the one app on any mount whose `hdiutil info` image path ends in `.dmg`. The launcher tests build their fixture image mount-free (`makehybrid`, then `convert` to UDZO) for the same reason, and unregister the stub app bundle the `open -W` test hands to Launch Services, since the entry outlives the scratch dir.
- Remote repos assume a POSIX shell, key-based login, and git on the non-interactive PATH of the host (the QNAP has no git, so it can be added but every card there errors). `remoteCommand` single-quotes each argv word; `tildeQuote` keeps a leading `~` bare so the remote expands it. Openers for a remote path run `ssh -t host 'cd … && …'` (kitty, Terminal, agent) or `code --folder-uri vscode-remote://ssh-remote+host/path`; Finder throws.
- SSE clients buffered through some proxies/sandboxes may look silent; verify reactivity in a real browser before debugging the watcher (the watcher path was correct all along the one time this came up).
- Runs deliberately do not use `@anthropic-ai/claude-agent-sdk` (it was tried and rolled back): jobs must run on the user's own `claude` install and Max login. The runner spawns `claude -p --input-format stream-json --output-format stream-json --permission-prompt-tool stdio`; the prompt goes down stdin as a `user` message, permission requests come back as `control_request` (`subtype: can_use_tool`) and are answered with a `control_response` carrying `{behavior, updatedInput}`. `AskUserQuestion` arrives the same way and is answered by returning `updatedInput.answers`. Stdin must stay open until the `result` message (the CLI exits once it is closed); a chat keeps it open past the result and writes the next `user` message to continue the session. `--setting-sources user,project,local` so CLAUDE.md and permission rules apply; MCP servers are off (`--strict-mcp-config` with no `--mcp-config`).
- claude-history's `--json` shapes are passed through as-is (snake_case types in `types.ts`); its README calls them an API for canopy's sake, so change both sides together. Its CLI answers a bad lookup as plain text with exit 0; `report()` in history.ts turns that into a 404. Days are local: the CLI buckets with sqlite `localtime` and canopy builds the day list with the OS clock, which agree in the server but not under `bun test` (Bun pins JS Dates to UTC there), so tests pass explicit dates.
- Design system lives entirely in `ui/src/styles.css` (bark/moss/lichen/rust/sky tokens as `light-dark()` pairs; the theme setting only flips `color-scheme` via `data-theme` on `<html>`). No CSS framework — keep it that way.
- A fleet resolves its workflow once, from the bundled and user sources only (not a repo's own `.canopy/workflows/`), since a fleet runs the same file over every repo it touches and a repo-local override would make that not true. `loadWorkflows` skips the repo source whenever `repo.host` is truthy (it assumes a remote repo, no local `.canopy/`), so the server asks with `loadWorkflows({ path: "", host: "none" })` — a fake host, not a fake path, is what actually suppresses it.
- The peer gate (`canopy peers gate`, what a peer's forced ssh command runs) clears every `GIT_*` variable from its own process env before doing anything else, since those are git's own env-config channel (`GIT_CONFIG_PARAMETERS`, `uploadpack.packObjectsHook`, and the like) and left in place would let a peer who can influence this process's environment run something the moment `git-upload-pack` or an in-process `git()` call touches the working tree. It then hands `git-upload-pack` an explicit minimal env of its own (`PATH`, `HOME`, `GIT_PROTOCOL` and `LANG`/`LC_ALL` when set) rather than the process environment, reads the serving machine's config read-only (no quarantine-and-rename), and refuses every command on a config it cannot read or parse rather than falling back to defaults. `sshd` must not `AcceptEnv` `GIT_*` or `BUN_*` for the same reason. The default accepts only `LANG`/`LC_*`, and `BUN_OPTIONS=--preload` reaching the gate would run code before it does.
