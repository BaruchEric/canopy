# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

canopy — multi-repo git cockpit (Bun + TS server, React 19 + Vite SPA, full CLI). See README.md for commands and features.

## Commands

- Gates: `bun run typecheck && bun run lint && bun test && bun run build` — all four before calling anything done. Build is required: the server serves `dist/web`, so a stale build shows stale UI.
- Single test file: `bun test src/core/git.test.ts`
- Dev: `bun run dev` (API :7850) + `bun run dev:web` (Vite :7851, proxies /api). Production mode is the built SPA served by the Bun server on :7850 only.

## Architecture

- `src/core/` — pure logic, no HTTP: host (locators: a repo path is absolute, or `ssh://<host><path>` for another machine; `parseLocator`, shell quoting, the ssh argv with a shared ControlMaster socket per host under the config dir; pure and tested), exec (`onHost(host, cmd)` runs here or over ssh, and `git()` routes by the repo's locator so nothing above it knows where a repo lives), scan (find `.git` dirs, never descend below a repo root; `scanSource` takes a `Source` and yields repos with ids `<source id>:<rel>`, bare under the launch root; the remote walk is one `find -L … -print0` mirrored from the local one plus `pruneNested`), git (porcelain-v2 parsing, all mutations; `getCommit` reads one commit with `--numstat -z` and `--name-status -z` joined on path, `getDiff` takes a `DiffTarget` union: worktree, untracked, or one commit's change to a file), suggest (claude CLI shellout with heuristic fallback), openers (macOS `open`-based launchers + .code-workspace/kitty-session generation; `agent` runs `claude` through the login interactive shell in a held kitty window, or Terminal via osascript when kitty is missing; every launcher takes the repo's `AgentSettings` and `claudeLine` turns them into the `claude …` shell line; the argv builders are pure and tested), herdr (the `herdr` opener: drives the herdr CLI's socket API to focus the workspace already at a repo's folder or create one and `agent start` Claude in its pane with the settings after `--`; the name/argv builders and the JSON readers are pure and tested, `openHerdr` is Bun), agent (browser-safe: `normalizeAgent` validates settings field by field, `claudeArgs` makes the flags, `splitArgs` reads the extra-flags box like a shell, `describeAgent` is the menu's one line), forge (a self-hosted Forgejo through its API: `apiBase` normalizes the address it was added as, `listForgeRepos` pages `/api/v1/user/repos` with a token read from a file or `$CANOPY_FORGEJO_TOKEN`, `forgeRepo` turns one API repo into a card with `status: null` and the forge's page as its `path`, `linkForgeClones` matches those cards to local clones by remote url and hands a clone the forge's page when it has no link of its own; everything but the fetch is pure and tested), meta (what a card says beyond git state: the remote as a web URL via `webUrl` in access.ts, and a one-line description from package.json/Cargo.toml/pyproject.toml, else the README's first prose line; read at scan time only, so a file event does not re-read it), store (config at `~/.config/canopy`, overridable via `$CANOPY_CONFIG_DIR` — tests rely on this; `sources` are the extra scanned folders, `addSource`/`removeSource`, ids slugged from labels and unique; `agents` are the per-repo agent settings keyed by repo path, `setAgent` drops an entry set back to the defaults, `agentFor` reads one), actions (browser-safe: labels, preconditions, and prompts for the Claude-driven actions; `chat` is the conversation, whose prompt keeps the safety rules and puts the first message last; tested), runner (Bun-only: spawns the `claude` binary per run with stream-json on both ends and the repo's agent settings as flags (yolo → `--permission-mode bypassPermissions`), folds its messages into a plain `Run`, parks on permission/question prompts until `answer()`; a chat run keeps stdin open after each `result`, goes `idle`, and `say()` sends the next user message down the same process (the first message spawns it); `stop()` on an idle chat closes stdin so the CLI exits and the chat is `done`; on end, re-reads status and sets `outcome` changed/unchanged via `statusFingerprint`), term (a shell inside canopy: `shellArgs` is the login interactive shell for a folder here or `sshSessionArgs` for one elsewhere, `termSize` clamps what the browser asks for, `parseTermMessage` reads the one text frame it sends, all pure and tested; `startTerm` is Bun-only, a `Bun.Terminal` pty with the shell spawned on it, closed with the socket), search (`grepArgs` is the `git grep -n -I --column -z -i -F -e … --` argv, `parseGrep` reads its `path\0line\0col\0text` records, drops leading indentation, clips a long line around the match through `clipLine`, and stops at `GREP_LIMIT` with `truncated`; `searchRepo` runs it through `git()` so a remote repo works the same and treats exit 1 as no match; `mapPool` is the bounded fan-out; all but `searchRepo` pure and tested), history (Bun-only: shells out to the claude-history CLI with `--json`; `historyOverview` matches repos to archive projects by realpath and folds `activity` into per-day arrays for the rings; `localDays`/`localMidnightIso` are pure and tested).
- `src/server/` — Bun.serve: REST + SSE (`/api/events`) + static. State holds one `SourceRuntime` per scanned folder (the launch root first, then config `sources`); `scanOne` swaps a source's repos into the aggregate `result` and `rebuildResult` reorders by source. One recursive `fs.watch` per local source maps changed paths (relative to that source) to the longest-matching repo via `repoRel`, debounces 400ms, re-reads status, broadcasts; ssh sources have no watcher and get their statuses re-read every `REMOTE_REFRESH` (5 min); a forgejo source is a server rather than a folder, so `scanSource` lists it through the API, it gets no watcher, and the same timer re-lists it. `rebuildResult` runs `linkForgeClones` over the whole tree, since which forge repos are already cloned here can only be told once every source is in one list, and every `/api/repos/*` route answers 400 for a repo with a `forge`: there is no checkout to run git in. Sources: `GET/POST/DELETE /api/sources` (POST validates: local paths must be directories and not overlap an existing local source, ssh hosts must match `isSshHost` and the path is resolved with `cd … && pwd -P` on the host; a 502 means ssh itself failed; a forge is proved by listing its repos, 400 for a bad address or a refused token, 502 for one that will not answer), `POST /api/sources/rescan?id=`, `GET /api/hosts` (aliases from `~/.ssh/config`), `GET /api/browse?path=&host=` (one folder's visible subfolders with a repo flag; local via readdir in `core/browse.ts`, remote as one `sh -c` script that prints `pwd -P` then `r name`/`d name` lines, parsed by `parseBrowse`). `/api/repos/run` answers 400 for a repo with a `host`. Runs: `POST /api/repos/run?id=` starts one, `/api/runs` lists, `/api/runs/answer|stop|say` and `DELETE /api/runs?id=` drive it (`say` is a chat's next message); every change broadcasts the whole `Run` as a `run` event (`run-gone` on dismiss). Agent settings: `GET /api/agents` is the whole map by repo path, `POST /api/repos/agent?id=` stores one repo's (normalized server-side) and broadcasts the map as an `agents` event; `/api/repos/open`, `/api/repos/run` and `/api/workspaces/open` read them. Drill: `GET /api/repos/commit?id=&hash=` (400 for a non-hash, 404 for an unknown one) and `GET /api/repos/diff?id=&file=&commit=&orig=` for one file's diff in that commit. Shells: `GET /api/term?id=&cols=&rows=` upgrades to a websocket (404 unknown repo, 400 forge, 426 without an upgrade); binary frames are keystrokes down and pty output up, a text frame is `{"resize":{"cols","rows"}}` down and `{"exit":code}` up before the close; the server keeps every open session in `state.terms` and ends them on stop. Search: `GET /api/repos/grep?id=&q=` is one repo, `POST /api/grep {q, ids}` is many (one `GrepRepoResult` per id in the order given, `GREP_CONCURRENCY` at a time, a failed repo carries `error` instead of failing the call); `grepQuery` refuses an empty, multi-line or over-long term with 400. `POST /api/repos/openfile?id=` `{file, line}` opens the file in VS Code through `openFile` in openers (`fileOpenArgs` is pure: `code -g path:line`, behind `--remote ssh-remote+host` for a remote repo). History: `GET /api/history` (the overview, memoized 5 min and per scan; `?refresh=1` forces), `GET /api/repos/sessions|session|search?id=` and `POST /api/repos/note?id=` (opens the vault note); all answer 503 with the reason when the CLI is missing and 404 when the repo has no project in the archive.
- `src/core/library.ts` + `lib/devhub/`: the bundled stdlib Python workspace manager, served lazily through Canopy at `/library/*`. `Library` owns an authenticated loopback worker; `canopy.py` canonicalizes the launch root, copies durable `_devhub` metadata once into `$CANOPY_CONFIG_DIR/library/<root-hash>`, and serializes CLI/HTTP/background writes. The Library/Ports views embed the existing dashboard editors inside the React shell; `bridge.js` handles same-origin repo navigation and theme updates. `canopy library --root <dir> <command>` shares the same state. Do not import generated snapshots, live PIDs, credentials, or personal deployment/DNS infrastructure into the repository. Regression coverage is in `src/core/library.test.ts` (real Python subprocess and HTTP integration, fixture workspace only).
- `src/cli/` — `bin/canopy.ts` entry; `render.ts` holds the ANSI tree renderer.
- `ui/` — separate tsconfig (both are typechecked). State in one Zustand store (`ui/src/store.ts`); server types imported directly from `src/core/types.ts` — keep that file browser-safe (no Bun/node imports). Per-browser preferences (grouping, open target, theme, density, and which of a forge's repos get cards) live in `ui/src/settings.ts` under localStorage `canopy.settings`; grouping logic is pure in `ui/src/grouping.ts` (tested). `ui/src/routes.ts` reads `?repo=&view=solo`, which renders one panel edge to edge for the new-tab / new-window targets, and `view=shell`, one shell the same way; `popupFeatures` sizes that window off the screen it opens on (pure and tested). `RepoLink` is the remote's glyph, on a card and in the panel head (it swallows its own click, middle click and Enter so the card underneath does not open); `RepoMenu` is the per-card ⋯ menu (portal-rendered, keyboard-navigable; chat, the jobs, agent, herdr and agent settings under "with claude", the plain apps under "open in"); `RunSheet` is the one modal (pre-flight, the run console with the chat's composer, the agent settings form, or the search across the repos in view); `RunChip` is the run's word on a card or panel. `TermDock.tsx` holds the shells: `TermView` is one xterm.js on the websocket, kept mounted and hidden when not showing so switching never ends a session (the theme is read off the CSS tokens through a probe element since `light-dark()` does not resolve in `getComputedStyle` of `:root`); `TermDock` is the strip along the bottom, `PanelShells` the foldable, drag-resizable section in a repo's panel, `ShellSolo` the `?repo=&view=shell` page a new tab or window shows. The store keeps every shell in `terms` with its `place` (panel or strip), `activeTerm` for the strip, and the persisted `termHeight` (strip) and `panelTermHeight` (panel shell); `openTerm` resolves the `shell` setting through the pure `shellPlace` in `settings.ts` (tested), opens the repo's panel and unfolds its shell section when the shell lands there, and `closePanel` drops a panel's shells (their views unmount and the ptys hang up) since a panel shell lives with its panel. The changes section is `ChangesList` in `Dock.tsx`: a filter box, a list/folders toggle, a header whose buttons sort on click and reorder by drag or Alt+arrow, and the rows on one grid (`.file-table`, rows through subgrid so the columns line up; the folders view adds a full-width heading row per folder, folders in the order their first sorted file comes); the column order, sort and view are the `fileCols`/`fileSort`/`fileView` settings, and the pure parts (`sortFiles`, `filterFiles`, `groupByFolder`, `moveCol`, `colOrder`) live in `ui/src/files.ts`, tested. Each file carries `mtime` from the server: `getStatus` stats every changed file (local via fs, remote through one `sh -c` loop that tries GNU then BSD stat), only for a repo with changes and best effort. Each panel section (changes, shell, search, history, claude) folds through `toggleSection`; the closed keys persist in `closedSections` (globally, not per repo; search, history and claude start folded). `Search.tsx` holds both search surfaces: `SearchSheet` (the magnifier in the top bar or ⌘⇧F; searches `visibleRepos` minus forge and unreadable ones through `api.grepAll`, one foldable row per repo with hits, and **panel** calls the store's `searchIn`, which closes the sheet, opens the repo's panel, unfolds its search section and leaves the term in `pendingSearch`) and `SearchSection` (the panel section, its own box scoped to one repo, which takes `pendingSearch` when it is for its repo and runs it). Hits render through `groupHits`/`markHit` in `ui/src/hits.ts` (pure, tested), and a hit click is `api.openFile`. A zustand selector that builds a new array (like `visibleRepos`) must go through `useShallow`, or the component re-renders forever and React unmounts the whole tree. A folded shell section hides its body with `display:none` rather than unmounting, so the pty keeps running; `TermGrip` drags the strip's or a panel shell's height (`edge` picks which way it grows). The store keeps `runs` by id, `agents` by repo path (`agentFor(s, repo)`), and `sheet` for what the modal shows. `history` in the store is the claude-history overview (fetched after first paint, on rescan, and every 10 min); `Rings` draws the per-day strip on cards and in the panel (levels from the pure `ui/src/rings.ts`, tested); `Claude` is the panel section (list, search, turn-by-turn detail, open note). `Commit` is the drill: `CommitRow` renders a log row as a button and, open, the commit's message, files with counts and bars, and per-file diffs; the panel's history and a session's commits both use it, one open at a time, keyed by hash. Details are cached per hash for the page's life since a commit never changes.
- Repo **ids** are paths relative to the scan root (prefixed `<source id>:` under an extra source); **workspaces store absolute paths** (stable across roots; a remote repo's is its `ssh://` locator). The API accepts ids and converts at the edge (`idToPath` in server).

## Conventions & gotchas

- `git status --porcelain=v2` paths are never quoted; fields split on single spaces with the path last (`splitN`). Rename entries carry `path\torig`.
- Untracked-file diffs use `git diff --no-index /dev/null <file>`, which exits 1 on success — don't treat that as an error.
- Remote repos assume a POSIX shell, key-based login, and git on the non-interactive PATH of the host (the QNAP has no git, so it can be added but every card there errors). `remoteCommand` single-quotes each argv word; `tildeQuote` keeps a leading `~` bare so the remote expands it. Openers for a remote path run `ssh -t host 'cd … && …'` (kitty, Terminal, agent) or `code --folder-uri vscode-remote://ssh-remote+host/path`; Finder throws.
- SSE clients buffered through some proxies/sandboxes may look silent; verify reactivity in a real browser before debugging the watcher (the watcher path was correct all along the one time this came up).
- Runs deliberately do not use `@anthropic-ai/claude-agent-sdk` (it was tried and rolled back): jobs must run on the user's own `claude` install and Max login. The runner spawns `claude -p --input-format stream-json --output-format stream-json --permission-prompt-tool stdio`; the prompt goes down stdin as a `user` message, permission requests come back as `control_request` (`subtype: can_use_tool`) and are answered with a `control_response` carrying `{behavior, updatedInput}`. `AskUserQuestion` arrives the same way and is answered by returning `updatedInput.answers`. Stdin must stay open until the `result` message (the CLI exits once it is closed); a chat keeps it open past the result and writes the next `user` message to continue the session. `--setting-sources user,project,local` so CLAUDE.md and permission rules apply; MCP servers are off (`--strict-mcp-config` with no `--mcp-config`).
- claude-history's `--json` shapes are passed through as-is (snake_case types in `types.ts`); its README calls them an API for canopy's sake, so change both sides together. Its CLI answers a bad lookup as plain text with exit 0; `report()` in history.ts turns that into a 404. Days are local: the CLI buckets with sqlite `localtime` and canopy builds the day list with the OS clock, which agree in the server but not under `bun test` (Bun pins JS Dates to UTC there), so tests pass explicit dates.
- Design system lives entirely in `ui/src/styles.css` (bark/moss/lichen/rust/sky tokens as `light-dark()` pairs; the theme setting only flips `color-scheme` via `data-theme` on `<html>`). No CSS framework — keep it that way.
