### FR-080 · A run beside what is going gets a worktree of its own
P2 · added 2026-11-22 · source: Eric ("what about spinning new canopy worktrees by defaults", 2026-11-22) · shipped 2026-11-22
FR-073 let several runs share a checkout, and sharing was what a second run got unless someone ticked a box. It now goes the other way. While something is going in a repo's checkout (a job, a chat between turns, a workspace run that holds the repo, or a workflow), a job's or a chat's pre-flight comes with **on a branch of its own** ticked and a line that says why. The run works in a worktree on a `run/` branch, and the landing queue lands it on main once Eric says land. Unticking the box starts it in the checkout beside the others, as FR-073 does. With the checkout free nothing changes.
The repo menu's **chat…** and **new chat…** and a tab row's **+ chat** used to start an idle chat at once. With the checkout in use they open the pre-flight, because a branch and its work item take their names from the first message. A chat on a branch cannot start with nothing said and is offered no best of N. The menu row's fact reads **own branch**. A run in a window of its own (`?view=run`) has no sheet, so **+ chat** there still starts a chat in the checkout.
The default is the page's. It sends `branch: true` for these starts, and the API and the CLI are unchanged: `canopy run` was already always on a branch, and a start that names no branch still works in the checkout. It holds for a local repo that is no seed while one of its three branch slots is free (`ownBranchBeside` in `ui/src/store.ts`, `branchByDefault` and `freeBranchSlots` in `ui/src/landing.ts`); with none free the run shares the checkout as before. Starts that carry the checkout's own context stay there: review notes sent to the agent, a failed move's fix, "merge with the agent" and the voice dock.
A chat on a branch differs from a checkout chat in two ways. It commits on its branch and does not push, so nothing it does reaches main or deploys until it has ended and been landed. And it holds one of the repo's three branch slots while it stays open. The sweep closes an idle one like any chat but writes no resume record for it: that resume would start the session in the checkout, where Claude keeps no such conversation, and the branch's landing record already carries it on.
Checked on the Mac on 2026-11-22 against a scratch server at 1440, 900 and 390 px: the box unticked with the checkout free, ticked with its line beside an idle chat, a chat started from **new chat…** on `run/w-…-answer-with-the-single-word-ok-u` that answered and waited for its next message, and **+ chat** unticked into the checkout.
Not done: no setting turns the default off for a machine or a repo, and a chat on a branch is landed only after it ends, since the queue takes a branch whose run has finished.

### FR-075 · Architecture Diagnosis of a repo (Archify's Code Analysis)
P2 · added 2026-11-22 · source: Eric ("do Recommendations", 2026-11-22, on the recommendation "Offer Architecture Diagnosis in canopy as a fourth kind in the map section") · shipped 2026-11-22
The map section's switch gains **diagnosis**: what reading the code finds, with the Code Analysis that Archify 3.3.0 brought into `lib/archify`. **analyze** has the backend run `code-analysis prepare` on the checkout, with no model and no run: it reads source for import cycles, package-level dependency cycles, hubs, modules that reach into another's internals and complex functions, and writes one page into `.archify/diagnosis/`, which keeps itself out of git. The section says how many findings and errors it found in how many files of which language, what changed since the analysis before, and the findings to look at first, then frames the page in the same sandbox a diagram gets. **save the file** downloads it and **remove** (pressed twice) deletes the folder. `canopy diagnosis <repo> [status|run|save|rm]` does the same. One language is read per analysis: auto lets the analysis choose, the select names one, and `.canopy/diagnosis.json` in a repo sets `language` and `exclude` globs for good. canopy leaves out what git ignores by itself, so a kept worktree or a build folder is never read. The analysis takes no config from the checkout, because Archify's config can name a program to run; canopy writes one that holds excludes alone. Checked on the Mac on 2026-11-22 against a scratch repo of 261 TypeScript files at 1440, 900 and 390 px: the first analyze, the result line and its three leads, a second analyze that said no change, the page's own copy button working inside the sandbox, save and remove. On canopy itself an analysis takes about 10 s and its page is 24 MB with `lib/**` left out, which `.canopy/diagnosis.json` here does.
Built in the kept tree `diagnosis`. The number skips two: on the day it shipped, two efforts still in flight had each taken FR-073 in their code (several runs in one checkout, and people and roles).
