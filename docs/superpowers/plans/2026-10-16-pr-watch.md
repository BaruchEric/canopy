# PR watch: a branch run opens a PR and keeps watching it (FR-011)

**Status:** shipped 2026-10-16. The spec's calls were made the same day
(see its "Calls made"): land or PR, a repo default for auto-merge in
`.canopy/prs.json`, write-access comments only, 3 attempts. Where the build
left the plan, the ledger's rulings say why; `docs/architecture.md` "The
PR watch" is the current description.

**Goal:** a ready branch run can push its branch and open a PR instead of
landing locally. Canopy then watches the PR: the footer shows its number,
diff size and a CI chip with the checks. Two per-run toggles, both off by
default, let a failed check or a trusted review comment start a fix run
that pushes to the PR branch, and let canopy merge once everything is
green on the same head commit.

**Spec:** `docs/superpowers/specs/2026-10-16-pr-watch-design.md`.

## What is there already

- Branch runs and their worktrees (`src/core/worktree.ts`,
  `startBranchRun` in `src/server/index.ts`), the ready state, and "fix it"
  (`LandingHub`, `fixPrompt` in `src/core/landing.ts`, `DriveSpec.resume`).
- `gh` is called through `exec` for the PR counts (`refreshPulls`,
  `src/server/index.ts`) and the launcher's PR list (`launcher.ts`). Its
  login is checked by `githubLogin` (`core/access`).
- Polling with no overlap and a health report: `src/server/health.ts`
  (`probe`, `every`, `passReport`).
- Records one JSON file each, written in order and adopted at start: the
  landing records in `<configDir>/landing/`.
- The run sheet: `Console`, `BranchBlock` and the footer in
  `ui/src/components/RunSheet.tsx`; the card chip in `RunChip.tsx`; inbox
  rows in `ui/src/inbox.ts`.

## Tasks

### 1. The model (`src/core/pr.ts`, pure)
- [ ] `PrState`, `PrCheck`, `PrWatch` in `src/core/types.ts` (browser-safe).
- [ ] `parsePrView(json)` over `gh pr view --json number,url,state,isDraft,additions,deletions,changedFiles,headRefOid,mergeable,mergeStateStatus,reviewDecision,statusCheckRollup,latestReviews`;
  map `CheckRun` and `StatusContext` entries to `pending | pass | fail | skip`.
- [ ] `parseComments(json)` and `trusted(comment, writers)`.
- [ ] `checksWord(state)`, `readyToMerge(state, watch)` with a reason for
  each blocker, `nextPoll(state, watch)` (30 s or 5 min or never).
- [ ] `fixPromptForCheck`, `fixPromptForComment`, and the attempt counter
  (3 per check name or comment id).
- [ ] `pr.test.ts` on recorded `gh` JSON.

### 2. Pushing (`src/core/worktree.ts`)
- [ ] `pushBranch(dir, remote, branch)`: `git push <remote>
  <branch>:<branch>`, never `--force`; `{ok}` or `{rejected, output}`.
- [ ] `pushRemote(repo)`: the upstream's remote, else `origin`, else the
  only remote, else none.
- [ ] Tests on a scratch repo with a bare remote.

### 3. The hub (`src/server/prs.ts`)
- [ ] `PrHub.open(run, {draft})`: the run must be ready (clean, ahead);
  push, `gh pr create`, record `RunBranch.pr`, take the run off the
  landing ready list. Refusals: no GitHub remote, `gh` not logged in, a
  dirty worktree.
- [ ] The watch loop: one timer, `nextPoll` per watch, no overlap, the
  `canopy:prs` health check, the `pr` event.
- [ ] Auto-fix: a failed check (log tail from `gh run view <id>
  --log-failed`) or a trusted new comment starts a resumed run on the
  worktree; one at a time per PR; a run that ends without a new head
  commit on the remote counts as a failed attempt.
- [ ] Auto-merge: `readyToMerge` on the head just read, then `gh pr merge
  <n> --match-head-commit <head> --<method>` from the main checkout (not
  `--delete-branch`, which switches the worktree off its branch), then
  `git push <remote> --delete <branch>`; then remove
  the worktree and branch and fetch the main checkout.
- [ ] The repo default: `.canopy/prs.json` (`{"autoMerge": true}`) read
  with `git show HEAD:.canopy/prs.json` in the main checkout when the PR
  opens, never from the run's worktree; a missing or unparseable file
  means off. Add `.canopy/prs.json` to canopy's own `.canopy/review.json`
  approve list.
- [ ] Records in `<configDir>/prs/<run id>.json`, adopted with the flows
  lock like the landing records.
- [ ] Routes: `POST /api/prs/open`, `POST /api/prs/set`, `GET /api/prs`.
- [ ] `prs.test.ts` with a fake `gh` on PATH (the cases in the spec's
  Testing section).

### 4. Landing (`src/server/landing.ts`)
- [ ] A run with `branch.pr` is not ready to land and not an orphan.
- [ ] The pre-flight's "open a PR when done" makes a run that settles

## Risks

- `statusCheckRollup` mixes check runs and commit statuses with different
  fields; the parser has to handle both, plus neutral and skipped.
- A required check that never reports holds auto-merge forever. The footer
  should say which check it is waiting on.
- GitHub's rate limit at a 30 s cadence across many PRs: one `gh pr view`
  per pending PR is fine for a handful, and the cadence backs off once
  checks settle.
