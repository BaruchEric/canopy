# Kit phase 3, part B: per-cell apply, skill adopt, tools

**Status:** shipped 2026-10-16 (3fec0f7), deployed to the mini the same day. Gates green (typecheck, lint, 3875 tests pass with 9 skipped, build). The dotclaude `tools` block is still to add, and that commit is Eric's.

**Goal:** the kit view fixes one cell at a time, takes over a hand-made skill
folder the way phase 2 takes over a hand-made MCP entry, and shows (and,
where no sudo is needed, installs) the tools `kit.json` lists.

**Spec:** `docs/superpowers/specs/2026-10-15-kit-secrets-phase-3-design.md`,
part B and call 3 of 2026-10-15. OpenClaw stays out (call 4).

## What is there already

- `POST /api/kit/apply {machine, actions}` takes a subset and refuses any
  action that is not in the current plan (`src/server/kit.ts` `apply`, 409).
  Per-cell apply needs no new route.
- A skill cell reads `foreign` ("a dir canopy did not place") when a wanted
  name is present but missing from the target's `.canopy-kit.json` `placed`
  (`src/core/kit.ts` `cell`). Apply never touches it: `link` refuses an
  existing path and `remove` and `relink` refuse anything but a link.
- MCP adopt keeps the old entry for put back (`adoptedFrom` in the ownership
  file, `restore` on the cell). Skill adopt follows the same shape.
- `KitManifest` has no `tools`, and the live `kit.json` has no `tools` block.

## Calls made while building (2026-10-15)

1. **A skill to adopt reads `adoptable`, not `foreign`.** The same state an
   MCP server's hand-made entry takes, so the glyph and the sheet say adopt
   is there. The store target and copy targets keep `foreign`.
2. **The adopted entry goes beside the skills dir**, at
   `<agent folder>/.canopy-kit-adopted/<name>` (`~/.codex/.canopy-kit-adopted/ship`),
   not `~/.canopy-kit-adopted/<agent>/<name>`. On the mini the canopy
   container's `~` is not a mount: a folder moved there would cross devices
   and be gone after the next recreate. The agent's folder is mounted, so the
   move is a rename on one filesystem.
3. **Put back takes the link text the kit placed** as its fourth word and
   refuses a link pointed elsewhere by hand, as the tests ask; a missing link
   is fine.
4. **An adopted name the store no longer holds keeps an `off` row** with
   `restore`, so put back stays reachable.
5. **Install takes `{machine, tool, line}`.** The page sends the line its
   confirm showed, and the server refuses one that differs from the cell's,
   so a kit.json edited between the look and the click never runs unseen.
   Install also needs the cell to read `missing` with a line.
6. **Checks see the login shell's PATH**, read once per machine from a marked
   line, so a check agrees with what an install in that login shell put on
   it. An `ID_LIKE` word picks the line when the `ID` has none (ubuntu takes
   `debian`).
7. **On the mini, tools are the container's.** The canopy service checks
   inside its container, not on the host. Its image is built `FROM shells`,
   so the check holds for the agents in the mini's shells. An install there
   would land in canopy's container alone and be gone at the next recreate,
   so a scan that ran in a container (`/.dockerenv` or `/run/.containerenv`)
   marks a missing tool `container`: the sheet shows its line to copy and
   says to add the tool to the Dockerfile's shells stage, and
   `/api/kit/install` refuses it (2026-10-16).
