# Best-of-N, plan 1: groups of one profile, a compare run and the winner lands (FR-033)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Status:** implemented and independently reviewed locally 2026-10-27 on `main`. Plan 2 remains open.

**Goal:** Start two or three branch runs for one note, dry-check each ready member, compare the green results, and land one winner while the group stays visible.

**Architecture:** Each member remains an ordinary branch run in its own worktree, linked by `Run.group` to a durable group record. The group hub scores ready members through a dry gate pass, starts one read-only compare run when multiple members are ready, and sends the winner through the existing landing queue. The winner's landing removes the other worktrees.

**Tech Stack:** Bun 1.4.2, TypeScript 7.0.2 with strict checks, `bun:test`, React 19.3.0, the existing HTTP API, landing queue, and cost ledger.

**Spec:** `docs/superpowers/specs/2026-10-25-best-of-n-design.md`

## Global constraints

- `times` is 1 to `GROUP_MAX` (3), and `GROUP_MAX` equals `BRANCH_RUNS_PER_REPO`.
- `times: 1` keeps the current single branch run behavior. For a group, absent `profiles` uses the repo's `job` route; one profile applies to every member.
- A `propose` group needs Claude Code. Reject an unusable profile and reject a group without enough free branch slots before cutting a branch.
- The group id is `g-<8 hex>`. Its records live in `<configDir>/landing/groups/<id>.json` and only the flows-lock holder writes them.
- Group auto-land is off by default. Losers stay until the winner lands, and `LOSER_KEEP` is 24 h.
- A member with scenarios is eligible only when `ScenarioRun.score >= minimum`, even if every per-scenario threshold passed. `scoreOf` stays the literal mean `P(yes)`; command results are 1 or 0.
- Keep files imported by the UI from `src/core/` browser-safe. Use strict TypeScript, no `any`, no `as` casts in signatures, and no new dependencies.
- Each task uses TDD and ends with its own test file, then `bun run typecheck`, `bun run lint`, `bun test`, `bun run build`, then a commit in the form `type(scope): lower-case summary`.

Plan 2 handles profiles per member, `reviewers: 2`, coordinator `times`, the costs fold, and collision suppression after FR-040 lands.

## Review focus

1. Invalid `times`, a non-branch request, or too few free slots refuses before any branch is cut. Task 4 pins this in `src/server/group-start.test.ts`.
2. A failure cutting or starting member three removes every branch already cut and leaves no partial group. Task 4 pins this in `src/server/group-start.test.ts`.
3. A dry setup or gate failure leaves the branch ready but makes it ineligible to win; a scenario score below `minimum` also fails even when every per-scenario threshold passed. Tasks 2 and 3 pin this in `src/server/landing.test.ts` and `src/server/groups.test.ts`.
4. A missing compare block, a non-member, or a ranking that omits a green member leaves the group at `needs-you` with the reviewer's closing text. Task 3 pins this in `src/server/groups.test.ts`.
5. A restart during `working`, `scoring`, or `reviewing` restores the group without scoring twice or starting duplicate reviewers. Task 3 pins this in `src/server/groups.test.ts`.

- `src/core/group.ts` owns the pure group types, scoring, compare prompt/parser, and display word.
- `src/server/landing.ts` runs and records a member's dry gates without rebasing or landing it.
- `src/server/groups.ts` owns group records, state changes, routes, reviewer scheduling, and loser cleanup.
- `src/server/index.ts` validates a group start, cuts and starts member branches, and wires group and landing events.
- `src/core/actions.ts`, `src/core/runner.ts`, and `src/core/costs.ts` carry the unlisted compare action and group ids through runs and cost rows.

Test this alongside a first member settling before the final `addMember`: no dry pass or reviewer starts early. ## Decisions this plan makes beyond the spec

- `expectedMembers` is persisted before fan-out, so a fast first member cannot trigger scoring before the other starts finish. A restart during an incomplete start holds the group for inspection. `GroupDry` and `MemberScore` carry branch and base explicitly so reviewer branch names can be mapped back to origins.
- The first plan supports one shared profile per group. A missing profile uses the repo's `job` route; plan 2 expands that one value into profiles per member.
- Keep the existing reviewer count at one. `reviewers: 2` and agreement between two rankings belong to plan 2.
- Apply the spec's recommendations: the reviewer is a run with read-only tools; a red member never wins; losers stay until the winner lands; auto-land is off by default; and `GROUP_MAX` is the three-slot cap.
- The spec lists `InboxItem` and `CostEntry` under `src/core/types.ts`, but current main defines them in `ui/src/inbox.ts` and `src/core/costs.ts`. Extend their actual definitions.
- The FR-032 scenario plan is planned, not shipped on main. Task 2 waits for it and consumes its named interfaces; group model, CLI, and UI work use the stable summary and route contracts above.
