# PWA and push, plan 1: an installable page with a shell-only service worker (FR-042)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Status:** planned 2026-10-26. Written on main at 1ac8fe7.

**Goal:** the page installs to a phone's home screen and a desktop's dock: a
manifest with icons rendered from the favicon, a hand-written service worker
at `/sw.js` that keeps one cache named after the build, holding the shell and
Vite's hashed assets and nothing from `/api` or `/library`, registered from
`main.tsx` on a secure built page, and a device tab row that says whether the
page is installed, how to install it, and what the worker holds.

**Architecture:** `ui/public/` gains the manifest and `icons/` (checked-in
PNGs, rendered once by `scripts/icons.ts`); `ui/index.html` links both. The
worker is `ui/sw.ts`, a second Vite build (`ui/vite.sw.config.ts`) into the
same `dist/web`, typechecked on its own (`ui/tsconfig.sw.json`, WebWorker
lib); its decisions are pure functions in `ui/src/worker.ts`, which the page
shares. `ui/src/install.ts` registers the worker, asks it to update when the
backend reports another build, and holds the state `InstallRow` reads in the
device tab. The server does not change: the SPA fallback already serves every
file in `dist/web` and Bun names `.webmanifest` `application/manifest+json`.

**Tech Stack:** Bun, TypeScript strict, React 19, Vite 8, bun:test. No new
dependencies; no PWA plugin. ImageMagick's `magick` renders the icons once.

**Spec:** `docs/superpowers/specs/2026-10-25-pwa-push-design.md`, the "Plans"
list's item 1 and the section "The installable page". The index is
`docs/superpowers/specs/2026-10-25-software-factory-borrowings-design.md`.
Plan 2 (keys, subscriptions, `core/push.ts`, `PushHub`, the routes, the
setting, the CLI, the health check) and plan 3 (the badge, the present hold's
tuning, `Retry-After`) are out of scope: this plan has no push code at all.

## Global constraints

- The manifest is `ui/public/manifest.webmanifest`, exactly: `name` and `short_name` `canopy`, `start_url` `/`, `scope` `/`, `display` `standalone`, `background_color` `#fafbf8`, `theme_color` `#fafbf8`, icons `/icons/canopy-192.png` (`192x192`), `/icons/canopy-512.png` (`512x512`) and `/icons/canopy-512-maskable.png` (`512x512`, `purpose` `maskable`), all `image/png`.
- `start_url` is `/` and never a backend, a `?repo=` or a `?view=`.
- `theme_color` stays the light bark `#fafbf8`; the dark one keeps coming from the two `theme-color` metas in `ui/index.html`.
- iOS reads `apple-touch-icon`: `ui/index.html` links `/icons/canopy-180.png` (180×180).
- The worker is `ui/sw.ts`, hand-written, under 150 lines, no workbox, built to `dist/web/sw.js` with no hash, since the registered path must stay `/sw.js`.
- Install pre-caches nothing. A navigation request is network-first with the cached shell as the offline fallback; `/assets/*` is cache-first; everything else (`/api/*`, `/library/*`, websockets, `/icons`) passes straight through, never cached, never read.
- The one cache is named `canopy-<build>` where `<build>` is `versionLine(__CANOPY_BUILD__)` from `core/version.ts`; activate deletes every cache whose name is not that.
- The page calls `registration.update()` when `/api/about` reports a server build other than its own (`sameBuild` from `core/version.ts` says so).
- Registration happens in `main.tsx` after the first render, only when `window.isSecureContext`, never on the Vite dev server (port 7851, or `import.meta.env.DEV`), and never under bun test (`main.tsx` does not run there).
- The worker never sees a token and holds no state beyond the cache.
- `ui/src/worker.ts` is imported by the worker and the page: ESNext only, no DOM-only globals, no Bun or node imports.
- Strict TypeScript with `noUncheckedIndexedAccess`; no `any`, no `as` casts.
- Plain words, no em dashes, sentence case headings (the unslop rules apply to docs and commit messages).
- All four gates pass before a task is done: `bun run typecheck`, `bun run lint`, `bun test`, `bun run build`.

## Review focus

Inputs the spec implies and no section of it names. Each has a test in the task that owns the code.

1. A `/sw.js` the server answers with `index.html` (a `dist/web` built before this plan, behind a newer page): the browser refuses the script for its MIME type, the page carries on as before, and the device tab shows that error rather than nothing (Task 5).
2. A navigation the edge answers with a redirect (Cloudflare Access's sign-in) or anything but a 200: handed to the browser untouched and never stored as the shell, so an offline open never paints a sign-in page (Task 3).
3. A request to `/api/*` or `/library/*`, including a navigation to the Library's own page, and a request for `/sw.js` or the manifest: the worker never answers it, from the cache or otherwise (Task 3).
4. A POST, or a GET to another backend's origin from the multi-backend page: passes, so a cross-origin asset is never cached under this origin's name (Task 3).
5. A page on plain http, on the Vite dev server or in a browser without service workers: nothing registers and the row says which it is in one line (Task 3 for the rule, Task 5 for the words).

```ts
export interface Icon {
  src: "canopy.svg" | "canopy-maskable.svg";
  out: string;
  size: number;
}
export const ICONS: readonly Icon[]; // 192, 512 and 180 from canopy.svg; 512 maskable from canopy-maskable.svg
/** the magick arguments for one icon: `-background none -density <3 × size> <dir>/<src> -resize <size>x<size> -depth 8 <dir>/<out>`;
 *  the density scales the 32-unit viewBox to `size` pixels at 96 dpi, so the resize is a guard */
export function magickArgs(dir: string, icon: Icon): string[];
```

`ui/public/icons/canopy.svg` is the favicon's SVG, decoded from the data URL, exactly:

```xml
<svg xmlns="http://www.w3.org/2000/svg" viewBox="0 0 32 32"><circle cx="11" cy="12" r="8" fill="#93c98b"/><circle cx="21" cy="10" r="7" fill="#6aa065"/><circle cx="17" cy="16" r="7" fill="#b8d9a8" fill-opacity="0.85"/><rect x="15" y="20" width="3" height="9" rx="1" fill="#7a5c44"/></svg>
```

`canopy-maskable.svg` is the same four shapes inside `<g transform="translate(6 6) scale(0.625)">`, after a `<rect width="32" height="32" fill="#fafbf8"/>`: the bark behind the circles, and the drawing held inside the safe zone a maskable icon keeps. That zone is a circle of radius 12.8 about the centre, and the scaled drawing's far corners sit under 12 units from it.

`scripts/icons.ts` run directly, under `import.meta.main`, renders every entry of `ICONS` with `Bun.spawnSync(["magick", ...magickArgs(dir, icon)])`, `dir` being `join(import.meta.dir, "../ui/public/icons")`, and exits 1 with `scripts/icons.ts needs ImageMagick's magick on PATH (brew install imagemagick); the PNGs are checked in, so only a changed SVG needs it` when `magick` is missing or fails. On the Mac it is `/opt/homebrew/bin/magick`, ImageMagick 7, whose own SVG renderer draws circles and rects fine.

### Task 3: the worker's rules

**Files:**
- Create: `ui/src/worker.ts`, `ui/src/worker.test.ts`

**Interfaces:**
- Consumes: `versionLine` and `sameBuild` from `src/core/version.ts`; `BuildInfo` from `src/core/types.ts`.
- Produces, all in `ui/src/worker.ts`:

```ts
/** the cache key the shell (index.html) is kept under */
export const SHELL = "/";
/** the one cache a build keeps: `canopy-<versionLine>`, `canopy-dev` for a bundle nothing stamped */
export function cacheName(build: BuildInfo | null): string;
export type FetchPlan = "shell" | "asset" | "pass";
/** what the worker does with one request: the shell for a navigation of the
 *  page's own origin, cache-first for `/assets/*`, and nothing at all for
 *  `/api`, `/library`, another origin, another method or anything else */
export function fetchPlan(req: { method: string; mode: string; url: string }, origin: string): FetchPlan;
/** whether an answer may be stored: a 200 of the page's own origin that no redirect produced */
export function keepable(res: { status: number; redirected: boolean; type: string }): boolean;
/** every cache name but the one this build keeps */
export function staleCaches(names: readonly string[], keep: string): string[];
/** whether the page registers the worker at all: a secure built page in a browser that has them */
export function shouldRegister(w: { secure: boolean; dev: boolean; port: string; hasWorker: boolean }): boolean;
/** whether the page asks its registration to look for a new worker: the server reports another build than the page's */
export function wantsUpdate(page: BuildInfo | null, server: BuildInfo | null): boolean;
```

`fetchPlan` in order: not `GET`, or `new URL(req.url).origin !== origin`, is `pass`; a pathname of `/library`, or starting with `/library/` or `/api/`, is `pass` whatever the mode; `mode === "navigate"` is `shell`; a pathname starting with `/assets/` is `asset`; else `pass`. `keepable` is `status === 200 && !redirected && type === "basic"`. `shouldRegister` is `secure && !dev && port !== "7851" && hasWorker`. `wantsUpdate` is both builds known and `!sameBuild`.

## Decisions this plan makes beyond the spec

- The icons are rendered by ImageMagick's `magick`, which the Mac has at `/opt/homebrew/bin/magick`, not by a library, and the PNGs are checked in; `scripts/icons.ts` runs only when an SVG changes. The source is the favicon's SVG from `index.html`, now a file at `ui/public/icons/canopy.svg`; the spec names no source icon beyond it, so nothing new is drawn.
- The spec's probes P1 and P2 are this plan's live check, items 5 and 6, since the manifest and the worker are what they probe; P3 and P4 wait for plans 2 and 3.
- "The bark background" of the maskable icon is the light bark `#fafbf8`, the manifest's own `background_color`, and the drawing is scaled by 0.625 about the centre to sit inside the maskable safe zone, which the spec does not mention.
- The `apple-touch-icon` file is `canopy-180.png`, rendered from the same SVG.
- The manifest link carries `crossorigin="use-credentials"`, since a cookieless manifest fetch behind Cloudflare Access gets the sign-in page. This is the plan's answer to the part of call 8 it can answer; whether Access lets `/sw.js` through with the cookie is checked live (item 5), not decided here.
- The worker is a second Vite build, not a second input of the page's config: with two inputs the shared `core/version.ts` would be split into a chunk both bundles import, and a worker that imports a chunk must be registered as a module worker; the spec's `inlineDynamicImports` does not stop that split and is refused with several inputs anyway. One input inlines everything.
- A third tsconfig (`ui/tsconfig.sw.json`, WebWorker lib, no `types`) checks the worker, because the DOM and WebWorker libs clash in one program; `bun run typecheck` runs all three.
- Install calls `skipWaiting` and activate `clients.claim`, so a new build's worker takes over open pages at once rather than after every tab closes. Safe because assets are addressed by their hash and the shell is network-first; the spec says only "on the next activate".
- The shell is stored under the key `/` (`SHELL`) from the latest plain 200 navigation answer; a redirect, an error or an opaque answer is passed through and never stored. The spec says "the cached `index.html`" without saying when it is cached.
- `cacheName(null)` is `canopy-dev` for a bundle nothing stamped; it never registers, so the name only keeps the function total.
- Registration also checks `import.meta.env.DEV`, beside the port 7851 the spec names, since a dev server on another port is still the dev server.
- The server does not change: no cache headers are added (the browser's update check bypasses the HTTP cache for `sw.js` by default, and Vite's assets carry their hash), and Bun already serves `.webmanifest` as `application/manifest+json`.
- The device tab's row is a new `InstallRow` after `NotifyRow`, with words of this plan's own, since the spec's device-tab words are plan 2's push words and only "share → Add to Home Screen" carries over, and an `install` button where Chrome offers `beforeinstallprompt`.
