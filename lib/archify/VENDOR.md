# canopy's copy of Archify

This folder is [Archify](https://github.com/tt-a1i/archify) by tt-a1i, Apache-2.0 at this release (see `skills/archify/LICENSE`, with `NOTICE` and the older releases' `LICENSE-MIT` beside it), at **3.3.0**, commit `af3aaf3c36762f2afb62a4a09533f6c7273b07e5` (2026-11-23). canopy uses it for the diagrams in the repo panel's map section and `canopy archify` (FR-071), and its Code Analysis module for the section's Architecture Diagnosis and `canopy diagnosis` (FR-075). `docs/architecture.md`, "Diagrams (Archify)" and "The map's Architecture Diagnosis", says how the pieces fit.

A diagram run loads this folder with `claude --plugin-dir lib/archify`, so the skill is `archify:archify`. The run calls the skill's CLI as `node lib/archify/skills/archify/bin/archify.mjs` by its absolute path, which is the command canopy's permission rule allows.

## What is here

- `skills/archify/`: upstream's `archify/` folder, the package its installer copies, byte for byte except that the rendered example pages `examples/*.html` are left out. They are about 830 KB each, 13 MB in all, and nothing at run time reads them: `doctor`, `demo` and the Type router use the example JSON files, which are kept. Since 3.3.0 the folder holds `modules/code-analysis/` too, 16 MB of the copy's 24 MB, MIT under its own `LICENSE` and `NOTICE`. A diagram run never calls it (below), though `finalize` imports two of its files to word its Architecture Diagnosis offer. canopy's backend calls one of its commands, `code-analysis prepare`, for the map section's diagnosis.
- `.claude-plugin/plugin.json`: canopy's own. Upstream ships no Claude plugin, only the skill, so canopy wraps it as one for `--plugin-dir`. Its version follows the skill's `package.json`, and a test holds the two, `skill-release.json`, the pin above and `ARCHIFY_VERSION` in `src/core/archify.ts` equal.
- `VENDOR.md`, this file.

## What canopy changed

Nothing inside `skills/archify/`. What canopy needs it gets from the outside:

- **The update check is off.** `finalize` and `deliver` fetch `https://tt-a1i.github.io/archify/skill-updates/archify/stable.json` to say when a newer Archify is out. canopy sets `ARCHIFY_UPDATE_CHECK_DISABLED=1` in a diagram run's env (`archifyEnv`), so that address is never asked. canopy's own health check `archify` asks upstream's tags instead, and `bun run archify:update` moves this copy (below).
- **The run's task** (`archifyTask` in `src/core/archify.ts`) names the folder under `.archify/` canopy chose, gives the CLI's absolute path, says to draw without source evidence in a checkout with no origin remote (Archify refuses `--repo-root` there, and the run would otherwise stop to ask), counts a finalize whose only miss is a browser check skipped for want of Chrome as delivered, and tells the run not to open the page, not to give the update notice, to make no explainer page beside the one asked for (3.3.0 makes them unasked by default), and never to write the `[archify explainer: …]` line into a rules file.
- **Code Analysis and the pull request commands ask first.** 3.3.0 added `start` and `code-analysis` (Architecture Diagnosis: a page served on loopback, extractors that run go, java and python, and a `duplicates.executable` in a config file that names any program), and `pr`, whose `attach` uploads images and writes a comment or the body of a pull request with the user's `gh`. A diagram run's rules (`ARCHIFY_COMMANDS` and `archifyTools` in `src/core/archify.ts`) name the commands that validate, render, check and repair a page, so those, `preview` and `demo` stop to ask. The task also says to leave the Architecture Diagnosis section out of the summary, which a passing `finalize architecture --repo-root` otherwise ends with. The page's own Code Analysis button only opens a dialog with a command to copy.
- **The Architecture Diagnosis is one command, called by canopy.** The backend runs `code-analysis prepare <checkout> --out <checkout>/.archify/diagnosis --locale en --config <canopy's file>` itself (`diagnosisArgs` in `src/core/diagnosis.ts`), with no model in the loop. `prepare` reads a config only from `--config`, and canopy's file holds `exclude` alone: the module's default excludes, what git ignores in the checkout, and the globs in the repo's `.canopy/diagnosis.json`. So `duplicates.executable` and `typescript.sdk` are never set, and the duplicate check stays off. JS/TS and Python are read by the parsers the module bundles. The other languages start a toolchain from PATH on a program of Archify's own, never the checkout's code: `go run` on its `extract.go`, `java` on its `SourceBindings.java`, python on its C and C++ script, and `cargo run --locked` on its Rust helper. Where a backend lacks the toolchain, as canopy's containers on the mini do for most of them, that language fails with the module's own words. After a run canopy deletes `analysis.previous/` and `analysis/raw-facts.json` from the folder.

Other addresses in the code, none of which a diagram run asks: `bin/preview.mjs` serves a page on loopback only when someone asks to preview one, and `renderers/shared/brand-marks.mjs` fetches a brand's logo only from a web address the user gives it. Since 3.3.0, `modules/code-analysis/lib/pull-request.mjs` asks `https://api.github.com/repos/…/pulls/…` (with `GH_TOKEN` or `GITHUB_TOKEN` when set) for `start --pr` and `code-analysis import-review`, `modules/code-analysis/bin/serve.mjs` serves on `127.0.0.1`, and `pr attach` reaches GitHub or GitLab through `gh`; all three sit behind commands that ask first, and none is reached by `prepare`. The one address a diagnosis can reach is crates.io: the first Rust analysis on a machine has cargo build Archify's helper (`modules/code-analysis/extract/rust/`, pinned by its `Cargo.lock`) into the temp dir, which downloads its crates. A page's footer links to Archify's repository and its new-issue form, which load only when someone clicks them. The rest are schema ids, links in the brand table and the docs, and the comments of the libraries Code Analysis bundles (TypeScript, chevrotain, lodash, three.js and others).

## Browser checks

`finalize` ends with `browser-check`, which drives Chrome, Chromium or Edge to measure the page. Where it finds none (canopy's own containers on the mini have none), it exits 2 with the gate `skipped` and the others passed, and canopy lists the diagram as "checked, no browser check". `ARCHIFY_CHROME` names a browser when one is installed somewhere unusual.

## Moving to a new release

`bun run archify:update` (`scripts/archify-update.ts`, the task `archify-update` in canopy's panel) does the mechanical part. canopy's health check `archify` runs `bun scripts/archify-update.ts --check` every six hours and goes down when upstream tags a release newer than the pin above.

1. Run `bun run archify:update` on a clean `main` (it refuses while `lib/archify` or `src/core/archify.ts` hold changes). It asks upstream for its `vX.Y.Z` tags, fetches the newest and the pinned release one commit deep without file contents, and checks out only `archify/` from each (the whole history is about 1.7 GB). It copies upstream's `archify/` onto `skills/archify/` file by file, leaving out `examples/*.html`, and merges any file canopy edited against the pinned release, leaving conflict markers when the two edits touch the same lines. It moves the version in the pin, `ARCHIFY_VERSION` and `.claude-plugin/plugin.json`, then runs `doctor` and canopy's Archify tests. `--ref TAG|BRANCH|COMMIT` takes another release; `--no-test` skips the checks.
2. Read what it printed. When it says the license files changed, read them and set the license in `.claude-plugin/plugin.json`, this file's first line and `src/core/archify.ts`'s header. 3.3.0 moved to Apache-2.0 (commit `9c306ee8`, "license: adopt Apache-2.0 while preserving historical MIT grants") and brought `NOTICE` and `LICENSE-MIT` into `archify/`. Keep both: Apache-2.0, section 4(d), asks for the NOTICE to travel with the copy.
3. Read the diff (`git diff --stat lib/archify`). For each web address the run lists as new, turn it off for a diagram run, by an env variable or the task, and name it here. Check SKILL.md's steps against `archifyTask`, and the CLI's path against `archifyTools`. Run `node lib/archify/skills/archify/bin/archify.mjs --help` and set each new command against `ARCHIFY_COMMANDS`: add one only when it reads and writes the files it is given and nothing else. For the diagnosis, check `code-analysis prepare`'s arguments and receipt against `diagnosisArgs` and `parseReceipt`, the keys of `overview.json` against `parseOverview`, and read `modules/code-analysis/config/defaults.json` for a new key that names a program or a path: canopy's config must keep leaving it unset. The update's tests run a real `prepare`, so a changed receipt or overview fails there.
4. Commit, push and deploy as for any change the backend serves. `git checkout -- lib/archify src/core/archify.ts` and `git clean -fd lib/archify` drop a run instead.

Diagrams drawn with the old release keep working: each page is standalone HTML.
