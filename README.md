# canopy

canopy is a workbench for building software with Claude across every repo you have and every machine they live on. It started as a multi-repo git cockpit: point it at `~/dev` and every repo under it is a live card with its branch, dirty files, ahead/behind and last change. It still is that. Around the board it grew the rest of the loop: a shell at every repo that outlives the page, Claude Code in those shells or driven as jobs, chats and workflows, the app's dev server run as a supervised task and framed right in the repo's panel, and the same screen on a laptop, a tablet or a phone. Web UI and a full CLI.

The write-capable, many-repo complement to [diffscope](../diffscope) (single-repo, read-only).

## User guides

Start with [Getting started](docs/guides/getting-started.md), or browse the [guide index](docs/guides/README.md) for step-by-step help with daily Git work, shells, tasks and previews, agents, workflows, and troubleshooting. The sections below provide the command and feature reference.

## TL;DR

- One screen for the whole grove. A Bun server finds every `.git` dir under the folders you give it (on this machine, over ssh, or on a Forgejo), shells out to `git`, watches the tree, and streams changes to a React SPA over SSE. Stage, commit (Claude writes the message if you ask), push, pull, drill into any commit's diff.
- Claude is the `claude` binary on the backend, with your login and your settings, never an API key or an SDK. It runs in canopy's shells, or canopy drives it over stdio for jobs, chats and multi-step workflows, relaying its permission prompts and questions to the browser.
- The dev loop lives in the panel: tasks run and supervise a repo's dev server, tests and builds on tmux, the preview frames the running app, and the project bench puts changes, app, shells and log on one screen.
- It usually runs as one always-on backend in a container on a Linux box on the tailnet (the mini), reached from any device over the tailnet or a Cloudflare tunnel. Shells survive a reload and a redeploy, and with keep shell history on, a reboot gives back each one's terminal and history. Several backends can share one board, with a repo checked out on two machines shown as one card. See `docs/deploy.md` and `docs/prd-shared-backend.md`.
- Bun + TypeScript (strict) server, React 19 + Vite + Zustand SPA, xterm.js, no CSS framework. `bun test`, `tsc --noEmit`, `oxlint`.
- **Run:** `bun install && bun run build && bun link`, then `canopy ui ~/dev`.

## What it is for

A few ideas decided most of what canopy grew into.

- **Walking away loses nothing.** A reload, a closed tab, a laptop that sleeps, a phone that drops off the network, a canopy redeploy: each shell is a session on a tmux server of canopy's own and keeps running, and the page rejoins it. With keep shell history on, a reboot of the backend brings each shell back with its screen and history, and a Claude shell with a one-click `claude --continue`.
- **Any device gets the whole core.** Git, shells, Claude, search, diffs, tasks and preview are the backend's and look the same from every browser. A phone gets a key bar under each shell, touch scrolling and pinch to size the text. Only the things that need a real desktop (kitty, Terminal, VS Code, Finder) go through a small helper on the machine you sit at. Without one they hide, and VS Code becomes a Remote-SSH link.
- **Your Claude, as you run it.** Every Claude canopy starts loads your user and project settings and CLAUDE.md files, with the model, effort and permissions you set per repo.
- **Several machines, one picture.** Multiple backends merge onto one board, and peers keep each machine's clones in step over git, pull-only, so work moves between machines only through git: a branch fast-forwards when that is safe, and a divergence or another machine's uncommitted work waits for you to take it.
- **Other people's repos are left alone.** The background fetch reaches only remotes you can push to or host yourself, and a cloned project's task file cannot start a process on its own.
- **Calm by default.** A new browser gets the guided panel: Claude in a shell, run my app, save my work. The advanced panel, with every section and chip, is one switch away.

canopy run pickup <flow>           # take a stopped branch flow up where it stopped; prints its id and status. Refused while another run works on its branch or the landing queue holds it, sent it back or landed it
canopy run prune                   # remove kept runs past the sweep's transcript span (30 days); a live branch's or an open PR's stays
canopy awake [off|always|working]  # keep this backend's machine from idle sleep: never, always, or while an agent of its own works
canopy plugins [--machine M] [--agent claude|codex]   # every Claude Code and Codex plugin on every kit machine: on, off, wanted by settings.json and not installed, or failing, with the MCP servers it brings
canopy plugins install|update|enable|disable|uninstall <name@marketplace> --machine M [--agent codex]   # through that agent's own CLI on that machine; codex has no update, and its enable and disable flip the enabled line in the plugin's own table in ~/.codex/config.toml
canopy plugins search [words] --machine M [--agent codex]   # what the machine's marketplaces offer, most installed first
canopy plugins marketplace add <owner/repo|url|path> | remove <name> | update <name> --machine M   # a marketplace runs what its plugins declare, so add only one you trust
canopy plugins commit [--machine M] [--dry-run]   # commit dotclaude's settings.json alone and push it, on the machine kit.json marks commits: true; prints what it holds first, by key name

## Web UI

- **Left rail.** The repo tree grouped by topic folder, with dirty counts rolled up. Drag its edge to resize; the panel-left button (or `[`) folds it away.
- **Seams.** Every edge between two parts drags: the tree, the cards, each dock column and row, a shell's height, split panes, a wide panel's summary column, the files list beside or over its file, the sessions view's side column and its agents list, the agents board's rail, Settings' list of sections and the clipboard's list. The arrows step a focused seam (Shift for bigger steps), Home and End go to its limits, and a double-click puts back the size canopy chose. A label by the pointer says the size while a handle is held. Sizes are kept per kind of screen, and a screen layout profile can carry them to another one. A diff, a task's log and a job's output scroll under a cap that the bottom edge of any one of them sets for all of its kind; the other capped outputs have a corner to pull one taller.
- **Center.** A dense card grid (auto-fills columns; ~16 across on a 7680px screen). Cards pulse when a repo changes on disk. Every card has a ⋯ menu: chat with Claude about the repo (**chat…**, in canopy), hand it a workflow (commit, push, ship, deploy, review) or a job (ask claude…), start an interactive Claude Code session at the repo (**agent**: a kitty window when kitty is installed, Terminal otherwise, held open at a prompt when the session ends; **herdr**: a [herdr](https://herdr.dev) workspace at the repo with Claude running in its pane, or the workspace the repo already has, focused), set the repo's **agent settings…**, open a **shell** at the repo inside canopy, or open the repo in kitty / Terminal / VS Code / Finder.
- **Live row.** A card with anything running on its repo shows it under the git line: a `✦` for each agent (sky and turning while it works, lichen once it stalls, a rust `⚑` while it waits on you, pale sky while it sits at its prompt with a shell, monitor or subagent still running in the background, dim when idle), `▶ dev :5173` for a task that is up (`↻` while it is being restarted, `✕` once it failed) and a cursor for each shell, blinking while a device has it open. A line runs from the marks to a few words on the most pressing of them, such as "needs you 4m", "stalled 12m", "background 4m" or "up 3h", and carries sap while an agent works. "Needs you" means a permission, a question or an open ask: a session that only finished its turn reads idle, the way Claude Code's own footer shows it. A stall is a working agent whose transcript has not moved for 10 minutes outside a tool call, or one tool call (a subagent excepted) open for 30. A mark grows in when its thing starts and drops off when it ends. After the words, past a dotted run of the line, the row keeps the last thing that left it for half an hour: "agent ended 3m ago", "test passed just now", "dev stopped 12m ago". On a card where nothing runs any more that trace is the whole row, and a row with no room for it leaves it out and says it in its tooltip. A click on the agents, the tasks, the shells or the trace opens them. The card's left edge asks in rust while an agent waits on you. Compact density keeps the `✦ n` and `▶ n` chips instead.
- **Agent settings.** Per repo: model (fable, opus, sonnet, haiku, or claude's own default), provider, effort (low to max), permissions (yolo, the default, for `--dangerously-skip-permissions`, or ask), and any extra flags for the claude command line. Saved on the server, keyed by repo path like workspaces, and applied wherever canopy starts Claude for that repo: the agent and herdr openers, workspace "open all" in agent or herdr, the CLI's `canopy open`, and every run and chat. The menu shows the current settings in one line; the sheet resets them in one click. A **provider** is an id: for Codex an entry in its own config, for Claude Code a settings file canopy keeps at `~/.config/canopy/providers/<id>.json` on the backend and passes as `--settings` to every Claude start on the route (shells, resumes, herdr panes, runs, chats, the commit-message suggestion, the ranger). Its `env` block names a gateway (`ANTHROPIC_BASE_URL`, `ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_MODEL`), so a route can run on a local model, such as a llama-server on the same machine, with all of Claude Code's tools and skills. A repo on another host and an incubator stage keep their own login, since the file is this machine's; canopy's config holds only the id.
- **Runs.** A Claude job opens a pre-flight dialog (what will happen, an optional note), then a console that follows Claude step by step: every command with its output, Claude's own remarks, and a lichen "needs you" block whenever Claude asks a question or wants permission for something outside the job (allow once, allow all for this run, or deny). While a run is going the card's leaf edge carries sap; when it waits, the edge and a top-bar pill turn lichen. Finished runs stay on the card until dismissed. A workflow that expects a change and ends without moving git status says "no change" instead of "done" (see Workflows), so a flow that found nothing to do is not mistaken for one that did something.
- **Landing queue.** A ready branch runs through the repo's rebase, gates and scenarios before it lands. A repo with a `setup` line can keep prepared worktrees per machine (`canopy worktrees warm`), so the next branch run can skip setup; when warm is wanted but unavailable, its first note says `no warm worktree; setup will run`.
- **Holdout scenarios.** Command checks and judge stories live outside the checkout. A judge that cannot answer holds the branch; the landing row, run sheet and waiting panel offer **land anyway**, which reruns command scenarios and explicitly leaves judges out. The sheet keeps the final score and omitted count after landing. Auto-merge on a PR runs the same set on the PR's head first and leaves a red one to you. The repo panel's landing section has a **scenarios n** chip that lists the set by name and kind; their text never reaches the page.
- **Work ledger.** Every branch run gets a durable work item, named in its branch and requested as a `Canopy-Work:` commit trailer. The landing queue, PR watch, triggers and coordinator add lines as it moves; `canopy work` reads and adds to the ledger. The agent is asked to end its closing message with a `## Handoff` heading and a line or two for whoever picks the work up next, which becomes a note on the item; every later run on the branch (fix it, resume, a PR's fix) gets the item's notes ahead of its message, fenced as data. The **work** view (`?view=work`, `g` then `w`) lists the items by state, the ones that need you first, with a search and a repo filter; a row opens the item with every note and a box for a new line, landed or drop by hand, and copy as markdown. A branch run's sheet shows the same block under its branch line.
- **From an issue.** A branch run whose note opens with `#123` or a GitHub issue URL starts from that issue: canopy reads it with `gh`, names the branch after it, and hands the agent its title, body, labels and latest comments (as data), then your own words. The run sheet shows "from issue #123" when it sees one.
- **Loadouts.** When `~/.claude/kit.json` has a `loadouts` block, the pre-flight of one plain run (no group, coordinator, workspace or remote checkout) shows a loadout select: a named harness, model, effort, skills and MCP servers, plus the repo's own skills and the `loadoutBase` skills. A plan, then build run is offered Claude Code loadouts only. The run gets those: every other user skill is turned off in a settings file of its own, and so is every installed plugin that has skills but none the loadout or `loadoutBase` names, whole, with its hooks and commands, since Claude Code cannot turn off one skill of a plugin. A plugin with no skills (hooks or commands only) stays on, and `<plugin>:*` in `loadoutBase` keeps any plugin on. - **Sweep.** The broom on the sessions view's status line and the agents board's bar (or `sweep` on the command line) opens a sheet of what went idle: shells with no input or output for a day, chats quiet for 12 hours, runs finished 3 days ago, open PRs the gh login authored with no activity on GitHub for 14 days (on any repo, from the one backend set to sweep PRs), and agents canopy did not start, listed only. Each row says where it is, how long it has been idle and why; everything starts ticked but the listed-only rows and a shell running a program in the foreground (a dev server, an editor, ssh), whose row names the program, and every PR: a close is public, so each is ticked by hand, a draft's row says it is a draft, and its title links to it on GitHub. **Close N** closes the ticked ones, each looked at again first, so a shell typed into since stays open and reads "in use now". The feed gets one line per close, and an agent panel or window whose agent a close ended goes with it. PRs are swept only by a backend whose "sweep PRs from this backend" switch is on, off by default and meant for one backend, since the list is the gh login's on every repo. A PR the sweep closes gets a comment saying so ("Closed by canopy's sweep after 14 days with no activity. Reopen it to pick it back up."), keeps its branch, and one canopy watches is read once a day for a reopen; a draft is never closed except by a tick. The Mac and the mini are assumed to run gh as the same login, which is how one backend's PR watch knows a close the other's sweep made. At each fire it closes those and puts the rest it could close in the inbox as one ask ("Sweep: 2 chats idle 12+ hours" when chats are not among them; with the default kinds there is usually none): **close all** closes every one in it, each looked at again first, **pick** opens the sheet with the same ones ticked, and **dismiss** closes nothing. A shell running a program is never closed on its own and never in the ask: only a tick in the sheet closes it. A newer fire replaces an ask left unanswered, and the slots a sleeping Mac missed fire once, within a minute of waking. The sweep tab and the ask belong to the page's home backend: each backend keeps its own schedule and its own ask, so an ask the Mac's schedule left shows only on a page whose home is the Mac.

- **Right dock.** Click any repo to pin a full detail panel. Its sections sit behind tabs, one showing at a time, down the left of a wide panel and across the top of a narrow one (the arrow keys walk them, and "sections as tabs" in the panel's gear turns them back into a stack of folds). The panel holds a file list with stage checkboxes (columns for the status letter, path, and when the file last changed on disk, newest first; click a heading to sort, drag one to reorder, type in the box to filter, or switch to **folders** for a heading per folder), inline diffs, commit box with **suggest** (Claude-written message), commit / commit+push, pull/push, openers, workspace membership, the commit log, and the repo's Claude sessions (below). Every commit in the log opens in place: the full hash (click to copy), author and time, the message body, then each file it touched with its status letter, lines added and removed, and a short bar (moss for added, rust for removed) scaled to the commit's biggest file. Click a file for the diff that commit made to it. Merges show against their first parent. The commits listed under a Claude session open the same way. Each of a panel's sections (changes, tasks, search, files, history, peers, preview, launch, claude, and the shells along its foot) folds by its heading, remembered per repo, and the open panels themselves come back after a reload. Panels stack side by side, so on an ultrawide you can hold half a dozen repos open at once; on a window 3200 px or wider a new column opens as wide as the room allows, up to 1200 px, with the cards keeping a third of the room or the width set at their seam, while narrower windows open every column at 440 px as before. Or set **open a repo** to **dock tabs** and the dock is one panel with the open repos as tabs across its top: a click on a card opens or brings forward its tab, a tab's × or a middle click closes it, and the tab beside it takes over. The panels behind the strip stay live, so a shell in one keeps running while another shows.

- **Capacity.** The top-bar chip shows available usage estimates, reported limit hits and resets for each backend. Unknown usage says no reading. Every start has a priority: what you start is interactive and never held; a PR's auto-fix, a coordinator's cards and a flow's later steps are normal and wait past 90% of the five-hour window or on a limit hit; triggers and best-of-N groups are low and wait past 70% (or 85% of the week). Held work waits where it lives (a queued trigger event, a coordinator card, a parked flow, a PR fix) and starts by itself after the reset; the chip and `canopy capacity` list it, with start anyway. A run that hits the limit waits for capacity rather than failing, and carries on after the reset; a second limit in a row fails it. The costs view sets the holds and `observedFiveHourUsd`, the estimate from the ledger; endpoint reads are not enabled.
- **Project bench.** ⧉ on a panel head (or on its preview, tasks or shells), or a double-click on the head, the repo's card or its row in the tree, brings the project to the front: its changes down the left, the running app, its shells under the app and the dev task's log beside them, all on one screen over a dimmed board. - **Gears.** Every panel, section, shell row and the feed has a ⚙ with its own zoom, its layout (fill the panel or the window, float in front, pop out into a window of its own), and share: copy its text, capture it as an image, or paste into it. A shell's copy is tmux's own clean text, not what the browser happened to draw. A panel's gear also reorders and hides its sections.
- **Remote activity.** Every five minutes (and once soon after start) the server fetches your own remotes of every local repo in the background. A remote is yours when it is on GitHub and you can push to it (your login's, or an org's that grants push, asked once through gh) or when it is self-hosted (a Forgejo on the LAN, a NAS, a path). A clone of someone else's project has no remote of yours and is left alone; a fork fetches your fork and not its upstream, so a busy upstream never reads as your own activity. A fetch that moves a ref re-reads that repo, which is what keeps the behind counts honest. When one of your remotes has a branch with a commit the checkout does not (a push from another machine, a branch a cloud agent opened, a PR nobody checked out here), the card and the panel head carry a `⇣ origin/branch` chip (left out when that branch is the upstream itself, since the behind count already says so), the card's time counts it as the repo's last change, and the `recent` grouping moves the card with it; the time's tooltip names the branch. The feed reports each branch that moved. Next to it, `⇄ 2` is the repo's open pull requests on GitHub, counted in one query over every repo the gh login can see and linked to the list. Set `"fetch": false` in the config to keep the server from fetching your repos (the pull request count is a gh query, not a fetch, and keeps coming). Without gh, only self-hosted remotes count as yours.
- **Work elsewhere in the repo.** A main checkout's card also says what the repo holds outside its own tree: `⧉ agent` for a linked worktree with uncommitted changes or commits the checkout does not have (Claude's agent worktrees under `.claude/worktrees/` included, canopy's own pull request builds left out), `⑂ idea +2` for a local branch checked out nowhere with commits HEAD lacks, and `≡ 2 stashed`. Several of a kind collapse to a count, and the tooltip lists each one. The panel's changes section has a row per item: a click on a worktree drills into its changed files (each opening its diff there) and the commits on its branch this checkout lacks, a click on a branch into its commits, each commit opening in place as in the log, and **open** goes to a worktree that is a card of its own. A worktree's row ends with how long ago its newest changed file was written, or its last commit made, so a tree an agent left reads as quiet. The feed reports a worktree's tree changing, a branch moving and the stash growing. The changes header reads live: the file count, `+12 −3` lines against HEAD (untracked files not counted), `↑2 not pushed`, `↓1 behind`, each peer's WIP, and the same `⧉ ⑂ ≡` chips as the card. The agents header counts the running agents by state, `1 waiting · 2 working`, rust while one waits. The view tabs carry live counts too (git: repos needing attention; agents: `✦ 4`, rust while one waits; health: checks down or healing; incubator: sprouts on the way), and each group heading in the grove sums its repos: `3● +87 −24 ↑2 ⧉ 1 ✦ 2 ⚑ 1` in the grid, where `✦ 2` is the agents working right now (its ✦ breathes) and `⚑ 1` the ones waiting on you, counting canopy's own runs and chats even with no broker; the narrow tree keeps the dirty count, the lines (`+1.2k`) and the agents, with the rest on hover. None of it counts toward the card's own dirty state or the `activity` grouping, which stay about this checkout. In the CLI they show as `⧉1 ⑂2 ≡1` after the summary.
- **A branch's app.** A branch run can run the repo's dev task in its worktree on a port from `CANOPY_TREE_PORTS`, from the run's sheet, the pre-flight toggle or `canopy worktrees start`, and show it in the repo's preview. A task's `env` takes `${PORT}`, `${PORT_2}`, `${PORT_3}` and `${WORKTREE}`. A `docker compose` task gets a stack per worktree, under a project canopy names; the compose file publishes `${PORT}`. Landing or dropping the branch runs `down -v`, stopping the task runs `down`, and canopy's own stack is refused.
- **Worktrees kept by hand.** A card's worktrees section keeps several worktrees for one repo at once, one per branch, the way worktrunk's `wt switch --create` does: `+ worktree` names a branch (new, from a base, or existing), and the tree lands under `~/.config/canopy/trees/<repo key>/<slug>/` with the repo's `setup` line run in it and the main checkout's ignored build caches (`node_modules`, `target`, `.env`) cloned in copy-on-write (APFS clonefile on a Mac, reflink on btrfs or XFS, a plain copy elsewhere). Each tree gets a port of its own, hashed from the branch into `CANOPY_TREE_PORTS` (default `7900-7949`) and walked past ports in use, so two dev servers never collide. A row shows the branch, `↑2 ↓1 ●3`, its port and open shells; **shell** and the agent button open a canopy shell in the tree with `PORT`, `CANOPY_TREE` and `CANOPY_TREE_PORT` set, **changes** drills into its files, and **remove** refuses a tree holding changes, unpushed commits or shells until told to lose them, with the branch kept or deleted. A tree follows its base by default: whenever the base moves (a commit in the main checkout, or the minute's check), canopy rebases the tree onto it with `git rebase --autostash`, so uncommitted work is stashed and put back. Commits the tree took from main that main has since amended or rebased are left behind instead of replayed over their new versions; **auto** on the row turns that off or on per tree, the form's **follow main** box sets it for a new tree, and **sync** shows while the tree is behind to run the rebase now. A tree with something at work in it (a test run, a build, a type check or an install, told by its name; or anything else there using a tenth of a core or more) is not rebased under it: the row says `sync waits on bun test`, and the tree follows at the next minute's check that finds it quiet. **sync** by hand does not wait. A rebase that stops on a conflict is aborted and said under the row, `sync stopped: …`, and is not tried again until the base moves or sync is clicked. **merge** is worktrunk's `wt merge` without the binary: it commits what is uncommitted, squashes the branch's commits into one (the first subject as the title, the rest listed), rebases onto the base, runs the repo's gates in the tree, fast-forwards the base (in the main checkout when it is checked out there, by moving the ref when it is checked out nowhere), then removes the tree and its branch. A step that cannot go on leaves the tree as it stood and says why under its row, `merge stopped: …` in rust until the next merge goes through: a conflict names the files and aborts the rebase, a failing gate shows its output, and the checkout's own changes to a file the branch touches name the file. The head's **clean up N** removes the trees whose base holds every commit and that hold no change or shell, branch and all, the way `wt remove` tidies a merged worktree. At cozy density the card itself lists the trees, a row each (`⑂ feat/x  ↑2 ●1 :7912 · 2h`, six at most and a count for the rest) with **shell** and the agent glyph to open one there and the branch opening the section; compact density keeps a `⑂ 2 trees` chip, rust while one's setup failed. Each tree is also a card of its own: the trees folder is scanned as a source, so a tree shows on the board as `canopy ⑂ feat/x` beside its repo, tagged **worktree**, with the whole panel under that name (changes, commit, files, tasks, preview, shells with `PORT` set), and **open** on a tree's row, the branch on a cozy card's row, and **open** in the changes section's work-elsewhere row all go to that panel. The CLI has the same under `canopy worktrees add|sync|auto|merge|clean|rm|path` (`merge` waits for the outcome and says why it stopped), and `eval "$(canopy worktrees shell-init)"` gives `cw <branch>` to cd into one. Only a repo on the backend's own disk keeps trees. A kept tree lands only through its merge; the branch runs' landing queue stays theirs.
- **Rings.** A card whose repo Claude has worked in this month carries a thin strip along its bottom edge: one column per local day, tinted in sap by that day's API-equivalent spend on a log scale shared by the whole grove. A quiet month leaves a faint ruler; a card Claude has never touched has no strip. Hover for the month's totals. The panel shows the same strip taller, with a tooltip per day.
- **Folders.** The root path in the top bar opens the list of folders canopy scans: the one it was started on, plus any you add, each with its repo count, a rescan, and a remove. Add a folder on this machine (changes show up live through a file watcher) or one on another host over ssh: pick a host from `~/.ssh/config`, give a path (`~/dev` works) or hit **browse** to walk the folders there one level at a time (repos are marked; breadcrumbs go back up; **hidden** lists the dot-folders too, which a scan skips unless one is the folder you add; "use this folder" fills the path), and its repos join the grove with a host tag on the card. Remote repos get status, log, diffs, stage, commit, push, pull, and AI-suggested messages the same way, every git call riding one shared ssh connection per host; they are re-read every five minutes instead of watched. The kitty, Terminal, and agent openers start an ssh session at the repo; VS Code opens it through Remote-SSH; Finder cannot. Claude runs stay local: the run action refuses a remote repo. Repos under an extra folder carry ids like `wsl-dev:web-apps/ripe` and group under the folder's label. A remote host needs key-based login, git on its PATH, and a POSIX shell.
- **Self-hosted git.** The third kind of source is a Forgejo (or Gitea) server rather than a folder: give its address and a file holding an API token, and canopy lists what the server holds through `/api/v1/user/repos`. Those repos are bare on the server, so their cards carry no working state: a dashed border, the forge's description, its default branch, and when it was last pushed to. Each one is matched against the clones already on this machine by remote url, so by default only the repos you have no clone of get a card, and the header of the folder list flips that to every repo. A clone with no web link of its own picks up the forge's page. Clicking a forge card opens that page; its ⋯ menu offers the page and the ssh clone url, and nothing else, since every git-driven route refuses a repo with no checkout. The token file's path is what gets stored, never the token; with no file named, `$CANOPY_FORGEJO_TOKEN` is read instead. The list is refreshed every five minutes.
- **Shells.** Your login shell on a real pty at the repo (an ssh session there for a remote repo), rendered by xterm.js and bridged over a websocket, opened from a card's menu (**shell**, in canopy). Where it lands is a setting: the repo's panel (a foldable section pinned along the panel's bottom edge with its own tabs and a + for another, five lines tall until you drag its top edge, each panel's shell its own height; double-click resets), the strip along the bottom of the window (one tab per shell; drag its top edge to size it, arrow keys work on it too, double-click resets), a browser tab or a small window of its own, or **auto**, the panel when the repo has one open and the strip otherwise. Closing a panel leaves its shells running: they sit in the shells picker meanwhile and come back as tabs when the panel opens again. Shells paint with the theme's own colors and follow a theme switch; a tab's × ends its shell. Shells live on the server, not the page: a reload, a closed tab or a dropped connection (the laptop asleep, the tunnel gone) leaves the shell and whatever runs in it going, and the window comes back to it, so a Claude session started in a canopy shell survives a reload. A dropped connection is rejoined on its own, first after a second and then at longer waits; a shell nobody has a tab for (opened in a window since closed) gets one where it was opened when the grove loads. With `tmux` installed, a shell survives the canopy server too: each one is a session on a tmux server of canopy's own (socket `tmux.sock` under the config dir, config `lib/tmux.conf`: no status bar, no prefix, so every key reaches the shell), each browser window on it is a client of its own, and a restarted canopy lists the sessions and hands the windows back to them, the last 2000 lines of what scrolled off ahead of the live screen. tmux draws on the terminal's normal screen, so xterm's own scrollback and mouse selection work as they would on a plain pty; the price is that tmux's copy mode and mouse handling are off. A remote repo's shell is the ssh session inside a local tmux session, so the other host needs no tmux. On a phone or tablet (a touch screen as the main pointer) a key bar sits under each shell with what a phone keyboard lacks: esc, tab, ⇧tab (Claude Code's mode), the arrows (held, they repeat), ^C, ^D, home, end, page up and down, a ⌨ that brings the keyboard up, and sticky **ctrl** and **alt**, lit until the next key from the bar or the keyboard (ctrl then `r` is ^R); the page shrinks for the on-screen keyboard rather than hiding the shells under it. A **paste** key reads the clipboard when the page is https or localhost (the tunnel, not the tailnet's plain http). A finger drag scrolls the shell (a program that owns the screen, like `less`, gets the arrows or wheel turns it would from a mouse), a flick keeps it going, and a pinch sizes the text, remembered per browser for every shell. A tap focuses the shell without bringing up the keyboard; the keyboard comes up only for the ⌨ key or a tap on a text field, anywhere in canopy, so a dialog opening or a shell connecting no longer pops it. `CANOPY_TMUX=0`, or no tmux on PATH, is the plain pty: the shell outlives its window with the last 512KB of what it wrote, and a canopy restart ends it (the tab says so and goes on the next reload).

## Voice

With `CANOPY_VOICE_KEY` (an ElevenLabs key) set on the backend, a mic shows in the top bar. Click it and talk: "what needs me?", "which repos have changes?", "open ripe". ## Tasks

A task is one of a repo's named processes (the dev server, tests, a typecheck, a build) that canopy runs and watches on the backend. Each one is a tmux session you can join and type into like a shell, with its output kept in a log on disk (`tasks/logs/` under the config dir, rotated when it grows) that stays searchable after the process ends.

canopy finds tasks on its own in `package.json` scripts, a `Cargo.toml` and a `Makefile`. A checked-in `.canopy/tasks.json` adds or changes them for everyone who clones the repo, and the edit sheet in the panel stores this machine's own changes in canopy's config, which win:

```json
[
  { "name": "dev", "cmd": "bun run dev", "dev": true, "keep": true, "withPanel": true },
  { "name": "e2e", "cmd": "bunx playwright test", "cwd": "web" },
  { "name": "lint", "hidden": true }
]
```

`dev` marks the task the preview pairs with, one per repo. `keep` restarts it when it fails (after 1, 2, 4 seconds and on up to a minute, giving up after five quick failures) and after the backend itself restarts. `withPanel` starts it when the repo's panel opens. `hidden` drops a detected task you do not want. `keep` and `withPanel` apply only in a repo whose remote is yours, so a project you cloned from someone else never starts a process by itself. Like shells, tasks survive a canopy redeploy. In a checkout with a `package.json` and no `node_modules` (a fresh clone), a task first runs the repo's `setup` line from `.canopy/gates.json`, or `bun install --frozen-lockfile` when the repo has none and keeps a `bun.lock`, and its log says so; a setup that fails fails the task.

The panel's **tasks** section lists them with start, stop, restart, a window of their own and edit. A card's live row marks its running tasks (a chip at compact density), and the top bar lists every running task across the grove. In the project bench the tasks sit along the side and the picked one's live terminal or log fills the log pane.

## The ranger

The ranger is canopy's always-on agent: one interactive Claude Code session that a backend keeps running in a folder of its own under the config dir, with the scan root added through `--add-dir` and the workspace's own `CLAUDE.md` loaded from there, so it sees every project. Settings can run it in the scan root itself instead, but Claude's trust in a folder covers every folder under it, so accepting the trust prompt there trusts every project, third-party clones included. Turn it on in Settings ("ranger") or with `canopy ranger on`. It lives on canopy's tmux, in the shells container on the mini, so a redeploy never touches it; when claude exits for any reason canopy starts it again on the same conversation (`--resume`), backing off and giving up after five quick exits in a row. Canopy moves it to a fresh conversation by hand, daily at a set hour (04:00 by default) and once the transcript passes a size (25 MB), only while it is idle; the brief then names the previous transcript.

It is told to look at the board through the API (`/api/tree`, `/api/runs`, `/api/tasks`, …) and to change a repo only by starting a run there. It never runs yolo, whatever its profile says, so anything its rules do not allow becomes an ask in the inbox. Three things wake it: a tailchan DM to its handle (`@ranger`, or the one set in Settings; each backend's must differ, and the second to start is told so), the crons set in Settings or with `canopy ranger wake --cron`, and the wakes it sets itself (`POST /api/ranger/wakes` with `when`, `cron` or `run`, which fires when that run ends). Canopy delivers a cron or a wake as a DM from its bot, tagged `[cron <id>]` or `[wake <id>]`, keeps them across restarts and holds them while there is no broker. With "it owns the Telegram bot" on, it starts with the telegram plugin and `--channels`; turn the plugin off in that machine's `~/.claude/settings.json`, or every other session there takes the bot back. Its first start stops at Claude's trust prompt for its folder: open it from the chip once and accept. A ranger that gives up shows in "waiting on you".

The top bar's `✦ ranger` chip (there while it is on) says what it is doing and opens its session, messages it, restarts it, starts a fresh conversation or turns it off, and lists its wakes.

```bash
canopy ranger [status]                     # what it is doing, its conversation and wakes
canopy ranger on | off | restart | fresh
canopy ranger say "look at the failing deploy"
canopy ranger wake in 30m "check the deploy"   # or 14:00, --cron "0 8 * * *", --run <id>
canopy ranger unwake <id>
```

## Health

Canopy watches its own pieces and says when one breaks: the tailchan, agent registry and asks streams, the ranger, the tmux server that holds the shells, the stage runner, each source's file watcher, the flows lock, and the fetch, remote and kept-shells passes. The pulse in the top bar is quiet while every check is well, lichen with a count while something heals and rust when something is down; open it for the list, or open the list as a dock panel or as its own page (`?view=health`, or `health` in the command line). Every row says why and since when, and opens to show its last 20 changes.

Pieces that are safe to restart heal themselves: a watcher that stopped is started again at waits of 1 s doubling to a minute, and after five heals that did not hold canopy stops, lists it in "waiting on you" and DMs you when tailchan is up. A tailchan stream with no bytes for a minute (the broker pings every 20 s) is dropped and dialed again. The ranger, tasks and the stage runner keep healing themselves as before and only report here. Taking over the flows lock from a canopy that is gone reruns the flows it left mid-step, so that one is a button, never automatic. Nothing heals the tmux server from here: compose restarts its container.

Repos can say what to check too. Put the checks in `.canopy/health.json`, or add them in the repo panel's health section, which keeps them in canopy's config for this machine:

```json
{
  "checks": [
    { "name": "site", "kind": "http", "url": "http://127.0.0.1:5173/", "while": "dev" },
    { "name": "dev", "kind": "task", "task": "dev", "heal": "auto" },
    { "name": "db", "kind": "compose", "service": "postgres", "heal": "button" },
    { "name": "smoke", "kind": "command", "run": "bun run smoke", "every": 300 }
  ]
}
```

A kind is `http` (2xx or 3xx, or `expect`), `port`, `task`, `compose` or `command` (exit 0). Any check may name a `fix` to run when it fails; without one a task check restarts its task and a compose check restarts its service. Any other check can name `"while": "dev"` to run only while that task runs and be off otherwise, so a dev server's URL stays quiet on a machine where you have not started it. A task check is off while its task is idle or stopped by hand, so a heal never starts a task you stopped. `heal` is `button` by default, `auto` to heal on its own with the same backoff and give-up, or `none`. The card shows the result in a word (`up · 42ms`, `2 of 3 up`, `down 3m`) and the `health` filter keeps the repos with a check down. A repo that is not yours (no remote you can push to) runs only the `http`, `port` and `task` checks from its own file, and its `auto` is a button; a repo on another host runs only `http` and `port`, and not ones aimed at `127.0.0.1` or `localhost`, which would be this machine; an incubator seed runs none of the ones that run in the checkout.

## Claude runs

Each run is one Claude Code session in the repo's directory: canopy spawns the `claude` binary on your PATH in print mode with stream-json on stdin and stdout, so it runs on whatever your terminal `claude` runs on (a Claude Max login included), with no SDK and no API key. It loads your user and project settings and CLAUDE.md files the way a terminal session would, but no MCP servers. `ask claude…` pre-allows only read-only git; a workflow step pre-allows what its `tools:` line names (see Workflows); anything else asks in the console. The repo's agent settings ride along: `--model` and `--effort` as set, and yolo runs the session in `bypassPermissions` mode, so nothing asks. Runs live in server memory: the last 60 finished ones stay visible until dismissed or the server restarts. Every run's redacted wire is kept under the config directory for 30 days; after a restart, a finished run opens read-only from its Costs row or Landing branch link, and `canopy run export <id> [--out file.md]` writes its kept record as Markdown. A finished run's sheet replays it from that wire: a kept run's opens with the replay bar, a live one's has "replay" in its footer; play at 1× or 4× (waits between steps capped at 3 seconds), scrub through the steps, or jump to a prompt, a message, a subagent's start or the result. A record a restart left without steps gets them back out of the wire. A finished run forks from a step of its replay ("fork from here" on the bar, "fork" in the footer for its end, or `canopy run fork`): a new run on a branch of its own, cut from the commit the original started at, that goes on from there with the original's context. On Claude the fork resumes a copy of the original's transcript cut after the step (`--fork-session`, so it gets an id of its own), on Codex the thread is forked, and a fork onto the other harness starts from a brief of the steps up to there; the fork's sheet says which. One run per repo at a time.

A chat is a run whose process outlives its first reply: stdin stays open after each `result`, the next message goes down it as another user message, and the CLI continues the session. Ending the chat closes stdin and the CLI exits on its own.

## Workflows

A workflow is a markdown file. Frontmatter names it and sets its precondition; each `##` heading names a step run through the same Runner a plain job uses. Steps form a graph through `after`, with a check and gate after each step's run. Files without the new keys keep their original chain order.

FR-034 plan 1 is implemented locally as of 2026-10-27, plan 2 (the graph on the flow sheet and `canopy workflow`) as of 2026-11-02, and plan 3 (the bundled ship and sentry-triage-fix as graphs) the same day; none has been deployed.

Frontmatter keys:

| key | meaning | default |
| --- | --- | --- |
| `name` | id, unique across the three sources, `[a-z0-9-]+` | file name without `.md` |
| `label` | menu text | name |
| `verb` | confirm button and the flow's title | label |
| `blurb` | one paragraph for the pre-flight | required |
| `when` | precondition: `dirty`, `unpushed`, `dirty-or-unpushed`, `any` | `any` |
| `expects-change` | a flow that leaves status untouched reports "no change" | false |
| `note` | placeholder for the note box; `note-required: true` makes it the task | optional |

A `##` heading is a step's name. The `key: value` lines right under it, up to the first blank line, are the step's keys; the rest of the section is the prompt:

| key | meaning | default |
| --- | --- | --- |
| `tools` | comma-separated: named sets `git-read`, `git-commit`, `git-push`, `bun`, `read`, or literal rules like `Bash(cargo:*)` | `git-read` |
| `turns` | max turns for this step's run | 30 |
| `check` | a shell command run in the repo after the run ends; exit 0 passes | none |
| `gate` | `continue`, `ask`, `verdict`, or `judge` | `continue` |
| `after` | comma-separated earlier step headings to wait for; all predecessors must settle before this step is ready; `none` waits for nothing, so a later step starts with the first | the step above, none for the first |
| `when` | comma-separated conditions on predecessors; any one holding runs the step, none skips it: `always`, `verdict done`, `verdict partial`, `verdict blocked`, `judge meets`, `judge partly`, `judge misses`, `check pass`, `check fail`, `changed`, `unchanged`, `skipped` | `always` |
| `mode` | `manual` holds the step before it starts until you continue; `auto` starts it when ready | `auto` |

A step whose body is empty is check-only: no Claude run, just the command. Workflows come from three folders, later ones winning by `name`: `lib/workflows/*.md` (bundled with canopy), `$CANOPY_CONFIG_DIR/workflows/*.md` (yours, `~/.config/canopy/workflows` by default), and `<repo>/.canopy/workflows/*.md` (that repo only, local repos only). The bundled five: **commit** (stages what belongs, writes the message, does not push), **push** (pushes the branch, rebasing only when safe), **ship** (gates, with a Docs reader beside them that reports which docs the change makes wrong, then commit, then push, stopping before committing if a gate fails), **deploy** (works out how the project deploys and runs it after its own gates), **review** (reads the diff and recent commits and reports what looks wrong, changing nothing).

Every step's `check`, when present, runs after the agent ends and before the gate. A nonzero exit normally fails the flow, or retries the step when configured. The `continue` gate releases its dependants, `ask` parks for you to continue, retry, or stop, and `verdict` asks Jev to evaluate the step's summary. The `judge` gate evaluates the work against the step's task and evidence. Evaluation needs `AI_GATEWAY_API_KEY` in the server's environment; without it, a `verdict` or `judge` gate parks for your decision.

Up to three ready steps run together, with at most one writer alongside the readers. A step counts as read-only when all its tool rules belong to `git-read` or `read` and its check is absent or `@gates`. A second writer waits with a reason naming the first. Every skipped step counts as settled for its dependants. Conditions match any predecessor in `after`; `skipped` can select a fallback. `changed` compares git-state fingerprints before and after that predecessor's agent run. An unreadable fingerprint counts real work as changed; skipped and check-only steps count as unchanged.

When a dependant uses `when: check fail`, its predecessor's failed check is recorded and routed to that dependant after retries are spent. This is the one check failure that lets the flow proceed. Verdict and judge refusals keep their existing retries and parks. At a park where the gate refused the work, retry goes back to the step its `back` names, with the reason and the refusing step's closing words, and continue goes on with the work as it is. After a park, continue keeps that result available to conditions on the next steps.

The repo's `.canopy/workflows.json` overrides step modes from the workflow file. For example, `{"modes":{"ship":{"Push":"manual"},"*":{"Deploy":"manual"}}}` holds Ship's Push step and any workflow's Deploy step. A workflow-specific entry wins over `*`. Canopy reads the committed file at the repo checkout's HEAD, so a dirty edit or a run's worktree cannot loosen that policy. An entry naming no step is a logged warning. A malformed committed file rejects a direct start with 400 and skips that repo in a fleet.

A trigger, fleet or incubator stage, including retro, refuses `ask` and `manual` steps before starting work. The reason names the step and whether its manual mode came from the workflow file or repo policy. A fleet records that repo's skipped reason and continues with eligible repos. Seeds never supply their own modes file.

A workflow that is not a chain draws as a graph on the flow sheet in place of the step strip: a box per step in columns by what it waits for, arrows for `after`, dashed arrows for `back`, a diamond before a step with a `when` and its conditions on the box's last line, a hand on a manual step, and the step's state as a word in its box. Click a box to follow that step, as with the strip. On a phone the strip stays and the graph folds under "graph". The pre-flight lists each step's `after`, `when` and mode, marks the ones `.canopy/workflows.json` decided with `(repo)`, shows that file's warnings, and will not start while the file is broken. `canopy workflow show|check|list` prints the same from a terminal.

A manual step shows `held` with `<step> waits for your go`. Continue or retry starts it; stop ends the flow. If a sibling parks or fails while another step is still live, the flow waits for the live work to finish before applying that park or failure. Stop stops all live runs and aborts checks. A restart preserves held steps without starting them, reruns interrupted steps with their saved sessions where possible, and retains a recorded pending failure or stop without launching more work.

Select several repos on the board (the select button in the top bar, or `x`) and run one workflow across all of them as a fleet: each repo whose precondition does not hold is skipped, the rest run up to three at a time, and the fleet's own sheet shows every repo's flow. Select mode starts with nothing picked. Click a card or a tree row to pick it, shift-click to pick (or unpick) everything from the last click to that one, tick a group heading to take the whole group, and use the bar along the bottom for all, none, invert, or just the repos in one state (with changes, unpushed, behind, and so on). ⌘A picks everything in view, Escape leaves. The count and the fleet only ever include picks the current filters show. All, none, invert and "only…" replace the selection with what is in view; a single pick a filter hides stays put and comes back when the filter clears.

## The shared repo spec

`spec/` is one spec for every repo canopy scans, versioned in `spec/manifest.json`: `SPEC.template.md`, a seven-section SPEC.md every repo keeps (what it is, who uses it, stack, how it is built and run, data, decisions, out of scope), and `DESIGN.md`, one visual system in Google's [DESIGN.md](https://github.com/google-labs-code/design.md) format (check it with `bunx @google/design.md@0.4.0 lint spec/DESIGN.md`). A repo adopts it with `canopy spec sync <repo>` or the bundled **spec** workflow, run on one repo or as a fleet: canopy writes marker blocks (`<!-- spec:begin vX.Y.Z -->…<!-- spec:end -->`) into SPEC.md and AGENTS.md or CLAUDE.md, DESIGN.md whole only for a repo that opts into the visual half (`--visual`), and records the version and each block's sha256 in `.canopy/spec.json` (going back to `--doc` removes the DESIGN.md it wrote, unless you edited it since); the workflow's agent then fills in a new SPEC.md's sections. Text outside the blocks stays the repo's. The scan reads each local checkout's state: **spec text in sync**, **behind** (an older version, untouched), **drifted** (a block or DESIGN.md edited by hand) or **not adopted**. A repo panel's folded **spec** section shows that state and syncs it (`sync`, **SPEC.md only** for `--doc`, **with DESIGN.md** for `--visual`), as does `spec sync <repo>` on the command line. The board's filter menu has **spec drift** and **no spec** chips, and the select bar can pick by them, so a fleet of the spec workflow brings every drifted repo up to date. "In sync" means the text matches, not that the code follows DESIGN.md. Bump the version in the manifest whenever the spec changes; every adopted repo then reads as behind.

Whether the sections are still true of the code is the bundled **spec-converge** workflow's job. A `schedule` trigger rule runs it on a cron line over every local repo (`{"name": "spec-weekly", "source": "schedule", "cron": "0 5 * * 1", "repo": "*", "workflow": "spec-converge", "land": "queue", "only": ["spec-adopted"]}` in `triggers.json`); it also runs from a card's menu or as a fleet. Its Check step reads the stack against the lockfile, the commands against the scripts, data and state against what the code writes, decisions against the commits since SPEC.md last changed, and out of scope against the tree, changing nothing, and ends with a report: `drift: 3` and one line per item, or `drift: none`. Its Fix step makes the named lines true, adds the dated decision lines, leaves the spec's own blocks and all code alone, and commits on a branch that lands through the landing queue. SPEC.md is a file every agent reads, so the branch always waits for **look and land**, with the report above the diff. The report shows folded under the event's row in the triggers view, as the first line on the branch's landing row and inbox item, and as one line in the repo panel's spec section ("drift checked 2 h ago: none", or "drift: 3, fix waiting to land" with a way to the run). The filter menu's **spec drift found** chip keeps the repos whose newest check found drift that no fix has landed for, and `canopy spec drift` prints each repo's newest report with where its fix stands.

`docs/workflows/example-update-deps.md` is a worked example meant to be copied to `$CANOPY_CONFIG_DIR/workflows/` rather than bundled, since a dependency bump belongs to you, not to canopy.

## Launcher

The launch section of a repo's panel (folded by default; **builds & releases** in the card's menu opens it) is a generic take on [freecad-launcher](https://github.com/deltahedra3d/freecad-launcher): where that app manages FreeCAD's AppImages and builds its pull requests, canopy does the same for any repo with a GitHub remote, on this machine.

- **releases** lists the repo's releases from GitHub (through `gh`, so its login and rate limits apply), each with the one asset that fits this machine: a glob from the launch settings when one is set, else a guess from the names (the OS and arch words, then the preferred kind: `.dmg` before `.zip` on a Mac, `.AppImage` before a tarball on Linux). A release whose assets name only other platforms says so instead of guessing. **install** downloads the asset into `~/.config/canopy/builds/<owner>/<name>/release/<tag>/` and opens it up: a disk image's `.app` or `.pkg` is copied out, a zip or tarball extracted (one wrapping folder lifted away), a bare binary or AppImage made executable. Several versions sit side by side.
- **pull requests** lists the open ones. **build** fetches `pull/<n>/head`, checks it out as a git worktree under `.../pr/<n>/` (the repo's own checkout is untouched), and runs the repo's build line there; a later build of the same PR refreshes the worktree. Pull requests are built on this machine only: a repo on another host lists them but cannot build them.
- **builds** is what is here: the installed releases, the built pull requests, and **this checkout** when the settings give it a run line. **launch** starts one: an `.app` through `open -n`, a binary directly, a checkout through its run line from its root, all through your login shell so PATH is what your terminal has. A first launch of a build asks once (**run it?**). A launched build shows as **running** with a **stop** button until it exits (an `.app` is watched through `open -W`, and stop quits it by its executable's path), and a binary's or run line's output lands in `.../logs/`. Launches are counted per build, with the last time. The ✕ removes an installed release or a worktree.
- **settings…** (also **launch settings…** in the menu) are four lines per repo, saved on the server like agent settings: `build` (run in a worktree after the fetch, and in this checkout on build), `run` (launches a checkout), `release asset` (the glob), and `launch a release` (how an installed release starts, `{file}` being what the download unpacked; blank opens it the way its kind says).

Downloads and builds are **jobs**: each shows in the section with its progress and the tail of its output, can be stopped, and reports to the event feed. Not carried over from freecad-launcher: the 3D preview and the `.desktop` entries, which are FreeCAD's and Linux's respectively.

## Claude sessions

Every session Claude Code has ever run in a repo, not only the ones canopy started, comes from [claude-history](../claude-history): the per-project archive and index of transcripts, prompts, tool calls, tokens, cost and the commits made while a session was running, from this Mac, the other hosts it pulls, and claude.ai/code. canopy shells out to that CLI's `--json` reports and never opens its sqlite file, so the archive's schema stays its own business.

The panel's **claude** section shows the all-time session count and API-equivalent spend, the rings, then the sessions themselves: newest first, the last 30 / 90 days or all of them, each row a title (or the first prompt), where it ran when that was not this machine, and what it cost. Open a row for the session turn by turn: your prompt, Claude's reply, and the tools it used, with the commits made during the session underneath. **open note** opens the session's markdown note from the memory vault in Obsidian (or whatever opens markdown). The search box runs the archive's full-text search over this repo's sessions; matches come back as rows with the matching passage.

canopy finds the CLI at `historyBin` in its config, else `claude-history` on PATH, else `~/dev/dev-tools/claude-history/bin/claude-history`. Without it the rings stay off and the section says why. The overview (every repo's totals and days) is two CLI calls, cached for five minutes and rebuilt after a rescan; the archive itself is refreshed by claude-history's own hourly sync, so a session shows up here within the hour after it ends. Dollar figures are list-price API equivalents of the tokens, as claude-history counts them, not a bill.

## Peers

Peers keeps a full clone of every repo under the launch root in sync across your machines over ssh, pull-only: each one fetches every other peer's branches and its uncommitted work as a WIP snapshot, fast-forwards what it safely can, and leaves a real divergence or a branch that only exists on a peer for you to look at. Nothing ever writes into another machine's working tree. A peer's ssh key runs only `git-upload-pack` and three read-only queries behind a forced command, never a shell. It replaces a one-way rsync mirror with the model coworkers use: every machine keeps its own clone and resolves its own conflicts, and work moves between clones only through git.

In canopy's config (`~/.config/canopy/config.json`, or `$CANOPY_CONFIG_DIR/config.json`):

```json
{
  "self": "mac",
  "peers": [
    { "name": "mini", "alias": "macmini-ts", "root": "dev", "role": "git" },
    { "name": "gpd", "alias": "gpd", "root": "dev", "role": "git", "repos": ["dev-tools/*", "web-apps/keel"] },
    { "name": "qnap", "alias": "nas", "root": "/share/Arik/dev-mirror", "role": "mirror" }
  ],
  "peerSync": "dry",
  "seed": [".env", ".env.local", ".env.*.local"]
}
```

`self` is this machine's own name; `peers` is who it pulls from, each an ssh_config `alias` (never `user@host`) and a workspace `root` (home-relative unless absolute). `role: "git"` is a full coworker; `role: "mirror"` only ever receives the rsync mirror and is never pulled from. `repos` is an optional list of globs over repo ids, a peer with it clones and fetches only matching repos. `peerSync` is `off`, `dry` (compute and report everything, write nothing but the fetched refs) or `on`. `seed` is the allowlist of ignored files (`.env` and the like) copied once from a peer when a repo lacks them, never overwritten.

```bash
canopy peers status                       this machine's name, sync mode, and its peers
canopy peers init                         set up each peer's git remote in every repo
canopy peers sync [id]                    fetch every peer once, fast-forward, list WIP
canopy peers take <id> <peer> [branch]    land a peer's WIP here
canopy peers track <id> <peer> <branch>   a local branch at a peer's tip
canopy peers seed <id>                    copy allowlisted ignored files from a peer
canopy peers gate --root dir              what a peer key's authorized_keys entry runs
```

The CLI's peers commands are not serialized with a running server, so while the server runs prefer the UI's actions, which queue behind its own pass.

`init`, `sync`, `take`, `track` and `seed` work on the folder this machine's running backend scans (`GET /api/peers` says which, and `--backend` picks the backend). Pass `--root dir` when no backend runs. They never fall back to the current directory, since `sync` clones every repo a peer has and this one lacks into that folder. The command refuses a backend that names itself as another machine.

A peer reaches this machine through a dedicated ssh key whose `authorized_keys` entry forces the gate and nothing else:

```
restrict,command="<path to bun> <path to canopy>/bin/canopy.ts peers gate --root dev" ssh-ed25519 AAAA... canopy-peer@<machine>
```

`sshd` must not `AcceptEnv` `GIT_*` or `BUN_*` for that key. The default config accepts only `LANG` and `LC_*`, and either one reaching the gate's environment could run code before it does anything.

## Project library and dev servers

Canopy includes `_devhub`'s workspace-management features. Run
`canopy ui ~/dev` and choose **library** or **ports** beside **git** in the top bar.
Library organizes projects and saved references with categories, tags, notes,
favorites, pins, archives, relations, sortable lists, and a file explorer. Its
project details link back to Canopy's Git panel. Ports manages assignments,
command detection, and starting, opening, stopping, and restarting dev servers.
Library also provides bulk Fetch/Sync and individual Fetch/Pull/Push/Sync.

These features require **Python 3.10+** and operate on the UI's launch folder.
Use the workspace parent (`~/dev` for the existing `_devhub`), not Canopy's own
checkout. Remote and Forgejo sources continue to work in the Git cockpit;
Library currently manages the local launch folder.

On first use, Canopy copies durable metadata from `<root>/_devhub` when present:
categories, overrides, links, notes, favorites, pins, archives, tags, references,
relations, and cached health. Your current uncommitted metadata is included.
The source files are left intact; subsequent edits go to
`~/.config/canopy/library/<root-hash>/` (or `$CANOPY_CONFIG_DIR/library/`). This is
a one-time migration, not two-way synchronization. Explicit project move/rename
and import actions still modify project folders, as they did in `_devhub`.

All library commands share that same state:

```bash
canopy library --root ~/dev --help
canopy library --root ~/dev doctor
canopy library --root ~/dev classify
canopy library --root ~/dev import https://example.org --title "A useful reference"
canopy library --root ~/dev tag my-project active personal
canopy library --root ~/dev note my-project "Next steps"
canopy library --root ~/dev relate my-project another-project
canopy library --root ~/dev attach "A useful reference" my-project
canopy library --root ~/dev set-link my-project --deployed https://example.org
canopy library --root ~/dev ports
canopy library --root ~/dev dev my-project --dry-run
canopy library --root ~/dev announce --project my-project --port 6100
canopy library --root ~/dev git sync
canopy library --root ~/dev build --no-fetch --no-check
canopy library --root ~/dev index
```

`build` discovers nested projects and deployment targets; omit `--no-check` for
live URL health checks and `--no-fetch` to fetch repositories. `index` exports a
static snapshot in the state directory without staging Git files. Refresh the
Library after CLI changes. Dev-server launching retains macOS Terminal/iTerm/Kitty
support. Canopy starts and stops its own library helper; no separate helper or
LaunchAgent is needed. Personal DNS setup and standalone gallery/endpoint-site
publishing stay in `_devhub`.

With several backends, `"librarySync": "on"` in each one's config shares the
Library's metadata between them: every minute each backend pulls the others'
entries over their `tailnet` URLs and merges them entry by entry, the newer
edit winning. The host keys (`host_root`, `terminal_app`, `trusted_origins`,
`helper_port`) stay per machine, and project folders are not moved yet. A backend
joins once, either as the starting copy or by taking another's whole; a second
`--adopt` is refused until its `sync.json` is removed. `"dry"` reports what a
pull would change and writes nothing; `"off"` refuses pulls, scheduled and from
the CLI alike. `--accept` is spent on the one pull it is given to, even when that
peer does not answer, so a hold still there on the next pull needs a new
`--accept`. A Library file missing on this backend is not read as a deletion of
what it held: its entries come back from the peer and nothing is tombstoned.

```bash
canopy library sync --seed                     # this backend's copy is the start
canopy library sync --adopt mac --backend URL  # that backend takes the Mac's copy
canopy library sync --status                   # each peer's last pull, and any hold
canopy library sync                            # pull now
canopy library sync --accept mac               # let a held mass deletion through
```

## Caller tokens

Under `enforce`, every call to the API needs a caller token in `X-Canopy-Token`, a read included; in the default `log` mode a call without one is logged, not refused. A caller with no token gets the page's own files, `GET /api/auth` (the mode and who it is), `/api/about`, `/api/going` (what a redeploy would cut off) and the pairing routes, so a page that is not signed in shows its sign-in and nothing else. Any token reads the board: the tree, the lists of runs, flows and shells, the notes, the event stream. What can hold anything copied, typed, printed or checked in takes a hand's token (a page's, the CLI's, a shell's): the clipboard, a shell's screen and text, tailchan's messages and files, a run read by its id, and everything read out of a repo (a file, a diff, the log, a search). The sweep's plan takes an admin's. A browser's event stream cannot send a header, so the page opens it with a one-use ticket its token asks for. A page, the CLI and a helper get theirs by pairing: the asker shows a code, a page that is already signed in approves it from the inbox, and `canopy auth login` or `canopy helper --pair` writes the token to a 0600 file in the config dir. While nobody is signed in, the backend prints a one-time first code to its log, which the sign-in strip (or `--code`) takes in place of an approval. Shells and the ranger carry their own token as `$CANOPY_TOKEN`. `canopy mcp` exposes the tools that token allows to the agent in the shell, through `claude mcp add canopy -- canopy mcp` or the kit, which writes the entry on each backend machine. `CANOPY_CALLERS=off|log|enforce` sets the mode; `log`, the default, counts what `enforce` would refuse and refuses nothing. `canopy auth status` and `GET /api/auth` show the count. See `docs/deploy.md`, "Caller tokens", for the rollout.

## State

- Config + workspaces: `~/.config/canopy/config.json` (override dir with `$CANOPY_CONFIG_DIR`). `historyBin` there points at the claude-history CLI when it is not on PATH; `fetch: false` turns the background fetch of your own repos off.
- Generated workspace files (`.code-workspace`, kitty sessions): `~/.config/canopy/workspaces/`.
- Next to the config: `tmux.sock` (the shells' tmux server), `shells/` (kept-shell snapshots, 0600), `pastes/` (images pasted into shells), `tasks/state.json` and `tasks/logs/` (what each task wants, how it last exited, its output), `ranger/` (the ranger's `state.json`, `wakes.json` and the `brief.md` it was last started with; a `ranger.md` beside the config replaces the bundled brief).
- Per-browser preferences (grouping, where a click opens, theme, level, text sizes, which sections show) live in that browser's localStorage, along with the open panels and shell tabs.
- Workspaces store absolute repo paths, so they work from any scan root. A repo on another host is stored as `ssh://<host><path>`.
- Agent settings live under `agents` in the same config, keyed the same way; a repo set back to the defaults loses its entry. Launch settings live under `launchers` the same way.
- Installed releases, pull request worktrees, launch counts and launch logs: `~/.config/canopy/builds/<owner>/<name>/` by the repo's GitHub slug (`_local/<name>-<hash>` for a repo without one), with a `state.json` per repo.
- Extra folders live under `sources` in the same config, each with an id, a label, a kind (`local`, `ssh` or `forgejo`), the host for ssh, and the absolute path, or for a forge its address and the path of the file holding its API token. The launch root is never stored. ssh control sockets sit next to the config as `ssh-*`.
